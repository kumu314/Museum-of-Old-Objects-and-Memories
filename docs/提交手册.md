# 拾物馆：提交与协作环境手册

版本：1.3\
更新日期：2026年10月24日\
适用基准：[开发书 v0.7](PROJECT_PLAN.md)、[AGENTS v1.1.1](../AGENTS.md)、[团队执行方案 v1.3](TEAM_EXECUTION_PLAN.md)

本手册约定团队的 Git 流程与开发环境。总仓库为 [kumu314/Museum-of-Old-Objects-and-Memories](https://github.com/kumu314/Museum-of-Old-Objects-and-Memories)，应用、数据库、工作台与三维原型已统一，提交钩子和 CI 已运行。实际工具链、启动与验证入口见 [运行说明](运行说明.md)。下列命令为操作示例，不表示已经执行，也不替代编码助手所需的 Git 操作授权。

**团队向同一个总仓库提交 PR。五个人可以同时开工，但需要先统一公共工程和最小接口约定，再在各自的任务分支里并行开发。**

当前已有统一公共工程，最终目标已改为方案 B 加自动建模。C 统筹用户归属、任务与资产契约，D 同步验证真实建模，A、B、E 分别推进动态展示、自助界面及测试素材。各成员持续负责到成品验收，分批 PR 只是合入方式。

## 一、仓库怎么组织？

团队采用：

**一个总仓库＋一个 `main` 主分支＋按任务创建的分支＋通过 PR 合入。**

五个人作为同一仓库的协作者，各自在自己的电脑上克隆项目、建立任务分支。拥有仓库写权限时，可以直接把任务分支推到总仓库，无须每个人再维护一个 fork。这属于 GitHub 的分支协作方式。[GitHub Docs](https://docs.github.com/en/get-started/using-github/github-flow)

分支可以这样命名：

| 成员 | 当前任务 | 分支示例 |
|---|---|---|
| A：Codex（用户本人） | 生成模型展示与检视 | `feat/generated-model-viewer` |
| B：另一位组员 | 个人工作台与生成预览 | `feat/self-service-studio` |
| C：工程负责人 | 用户归属与持久化生成任务 | `feat/generation-jobs` |
| D：Python/Django 组员 | 真实照片建模适配器 | `feat/model-generation` |
| E：内容与验收负责人 | 自助流程与生成质量验收 | `test/self-service-flow` |

**按任务建分支。** 一项任务合入后，下一项任务从更新后的 `main` 创建新分支，避免一个人的长期分支积累大量互不相关的改动。

现有零依赖检查入口为 `bash scripts/install-hooks.sh`、`node scripts/scan-noise.mjs` 与 `bash scripts/check.sh`。钩子检查提交格式、敏感文件、生成物、空壳代码和调试残留，不设置固定的提交行数或单文件体积上限。按独立任务和语义范围组织提交，素材是否入库由项目用途、许可与实际存储方案决定。提交格式沿用 `type(scope): 中文简述`，不自行添加 AI 署名。类型、业务测试、实库验证和构建检查已接入，具体入口与验证边界以运行说明为准。

Git 自动生成的合并标题（例如 `Merge remote-tracking branch 'origin/main' into ...`）使用 Git 默认格式，本地钩子与 CI 采用同一规则：提交前必须存在进行中的合并，历史记录必须具有多个父提交。普通提交即使以 `Merge` 开头仍须遵守常规格式；自定义的合并标题也须遵守常规格式。此处理参考 [commitlint 的默认合并标题规则](https://github.com/conventional-changelog/commitlint/blob/master/%40commitlint/is-ignored/src/defaults.ts)，并增加 Git 元数据核验。`scripts/check.sh` 同时运行零依赖的真实 Git 回归测试，入口为 `node --test scripts/lint-commit.test.mjs`。

每个人的工作流程就是：

1. 同步总仓库最新的 `main`。
2. 为本次任务建立分支。
3. 在自己的范围内开发、检查。
4. 提交并推送到自己的任务分支。
5. 创建 PR，目标分支选择 `main`。
6. 根据反馈修正，通过检查后合入。
7. 下一项任务重新从最新 `main` 开始。

PR 可以提前开成 **Draft PR**，方便其他人查看接口和进展；准备好合入后再转为正式待审状态。[GitHub Docs](https://docs.github.com/en/get-started/using-github/github-flow)

## 二、哪些东西需要先统一？

### 在已有公共工程上对齐新增契约

保留并维护下列已有基础；新增契约按实际依赖分批落实：

- 确定的框架、依赖版本和锁文件。
- 统一的目录结构。
- 能启动的基础页面。
- 类型检查、lint、测试和构建的实际入口。
- 本手册及开发书、AGENTS.md、团队执行方案，共四份项目文档。
- 最小共享数据结构、接口输入输出和错误格式。
- 一份符合共享结构、明确标识为测试数据的样例。
- 第八节约定的工具链版本、无密钥配置样例、开发数据目录和新环境复现说明。

这里的“最小接口约定”，例如：

- 一件展品有哪些公开展示字段？
- 展柜使用哪个字段选择模型和柜格？
- 保存时怎样携带版本？
- 文字 AI 与三维生成分别接收什么输入、如何跟踪任务和返回资产？
- 用户归属、任务去重、重启核对、过期结果和模型版本如何表达？
- 发布失败时，前端怎样知道哪些展品未确认？

**把这些约定清楚，各模块就能分别开发。真实接口可以随后逐步接入。**

不需要在这一阶段设计完全部数据库字段和所有未来功能。先让当前任务依赖的部分清楚、可用即可。

## 五、PR 谁来审核和合并？

**C 统筹合并，相关成员负责复核**，不用让每一个 PR 都等五个人看完。C 暂时无法参与时，由 A 在该 PR 中指定有仓库写权限的代合并人；代合并人核对既有复核与检查结果，不因此免除门禁。

| PR 内容 | 建议复核安排 |
|---|---|
| A 的 3D 交互 | B 核对界面接口，E 检查实际操作效果；C 看工程影响 |
| B 的工作台和故事面板 | A 检查体验，C 核对数据与接口使用 |
| C 的权限、发布、数据库变更 | D 复核相关规则，A 验收发布流程，E 提供复现和验收结果 |
| D 的 AI 与素材处理 | C 复核技术边界，E 检查内容与异常样例 |
| E 的样例、校验脚本和测试 | 对应模块负责人核对预期是否正确 |

C 自己提交的关键后端变更，也需要相应的复核，不能因为负责集成就免于检查。涉及共同实现时，不能把作者对自己所写部分的检查记作独立复核；无法安排非作者时按开发书第 7.1 节执行。

团队合入约定：

- 初始化完成后的 `main` 一律通过 PR 更新，不直接推送业务变更；首个空仓库初始化由 C 在获授权后完成。
- PR 统一使用 **Squash and merge**，一项任务形成一个合入提交；标题采用 `type(scope): 中文简述`，例如 `feat(cabinet): 完成展品检视与返回`。不加入 AI 署名。
- 作者确认改动范围和敏感内容，完成实际相关验证；对应复核人给出明确结论，阻塞意见已解决，依赖 PR 已合入，CI 要求的检查已通过，才能合入。文案等低风险改动按相关范围检查，不强制执行完整业务验收。
- PR 就绪后若 `main` 已变化，先按第七节更新任务分支，重新运行受影响检查；涉及权限、发布或迁移的修改需要复核更新后的实际差异。
- Squash 合入后关闭该任务分支的开发，下一项从最新 `main` 新建。删除远程任务分支前确认无人继续依赖它；本地分支若提示未合并，不直接用强制删除绕过提示。
- 人员或平台暂时不能满足复核条件时，只交接 Draft PR 或注明未验收的成果，不以关闭检查或强推完成合入。

仓库支持相应功能时，C 给 `main` 配置 PR、复核和状态检查要求，限制强推、删除与绕过保护；检查名以真实 CI 为准。平台不能提供保护时，仍按上述人工流程执行并保留 PR 证据。GitHub 的分支保护支持这些限制，具体可用能力取决于仓库和账号方案。[GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

`main` 的目标是：**能够启动和构建，已实现的功能正常运行。** 某个新增模块可以尚未完整接入，但不能让未完成的改动破坏已有流程。

## 六、你们尤其要避免的三种协作方式

### 1. 五个人分别初始化一套项目

公共工程由 C 统一建立，其他人从同一基础继续。否则，框架版本、目录、组件库和依赖很容易出现差异。

### 2. 每个人做完整个模块，最后才提交一个巨大 PR

把任务拆成能单独验证的小成果。例如你的展柜可以分别交付：

- 柜体和模型加载。
- 选择与检视。
- 返回和快速切换处理。
- 与故事面板的联动。

每个 PR 说明它解决的问题、实际验证和剩余部分。这样其他人可以逐步接入。

### 3. 为了让自己的模块运行，随手修改公共文件

共享 schema、数据库迁移、锁文件和根配置由 C 统筹。需要修改时，先说明具体需求和影响，再由明确的一位成员执行。

**从现有工程继续，C 与 D 优先对齐用户归属、持久化任务和真实建模，A、B、E 同步推进展示、界面和试用。各模块按依赖分批合入，作者持续承担联调修复直到最终产品验收。**

## 七、从首次克隆到提交 PR

以下示例适用于 Git 命令行。任务分支和文件路径必须替换为实际值；示例分支尚未为任何成员创建。每个代码块分步执行，前一步报错时先处理，不继续粘贴下一块。

### 1. 首次取得工程

C 核对总仓库的协作者权限，在公共工程就绪后补齐运行说明和应用检查入口。每人在自己的开发目录克隆一次，目标目录应不存在；不要把命令用于覆盖现有的文档目录或他人的 checkout。

```sh
git clone https://github.com/kumu314/Museum-of-Old-Objects-and-Memories.git heikesong
cd heikesong
git remote -v
git --no-pager status --short --branch
```

核对 `origin` 指向总仓库，再按第八节安装固定版本工具链与依赖。已有 checkout 的成员跳过克隆，不重复初始化工程。

### 2. 同步并开始一个任务

先查看工作区。若存在未提交或未跟踪内容，先确认归属：本任务内容可以在正确分支中做明确的阶段提交；其他任务内容由其作者妥善保存。不要为了得到“干净状态”直接丢弃文件、硬重置，或把不相关文件一并提交。只有工作区已妥善处理后再执行：

```sh
git fetch origin
git switch main
git merge --ff-only origin/main
git switch -c feat/cabinet-inspection
```

`--ff-only` 失败表示本地与远端历史需要核对；先联系 C，不用硬重置覆盖本地提交。示例任务分支已存在时，先判断它是否属于当前任务；不要删除旧分支来腾出名字。

### 3. 检查并提交本次文件

修改前阅读目录规则，完成后运行工程中真实存在的相关检查。先检查所有差异，再逐个暂存本任务文件。以下 `path/to/changed-file` 是占位路径，可按需要增加多个实际文件：

```sh
git --no-pager status --short --branch
git --no-pager diff
git --no-pager diff --check
git add -- path/to/changed-file
git --no-pager diff --cached --stat
git --no-pager diff --cached
git --no-pager diff --cached --check
```

确认暂存区没有其他人的工作、真实配置、密钥、客户素材、数据库或构建产物。检查无误且必要验证通过后再提交：

```sh
git commit -m 'feat(cabinet): 完成展品检视与返回'
git push -u origin feat/cabinet-inspection
```

后续修改继续提交到同一任务分支，不另建内容重复的 PR。不要把 `git add .` 作为默认步骤。

### 4. 更新进行中的任务分支

团队统一使用合并方式吸收最新 `main`，不要求成员重写已经推送的历史。先确认当前就是自己的任务分支，且未提交工作已经妥善保存：

```sh
git --no-pager status --short --branch
git fetch origin
git merge --no-edit origin/main
```

发生冲突时，先查看 `git status`，由冲突文件的责任人一起核对双方意图。修改冲突文件后，仅暂存解决过的相关文件，检查暂存差异，再用 `git merge --continue` 完成合并；重新运行受影响验证后再推送。

暂时无法解决、且确实处于本次 merge 中时，可用 `git merge --abort` 退出；退出会撤掉本次冲突解决过程中的修改，需要保留的手工编辑应先另行保存。本节要求合并前工作区干净，不依赖 abort 恢复未保存的旧工作。Git 官方也提示未提交修改可能使合并回退不完整。[git merge 文档](https://git-scm.com/docs/git-merge)

推送被拒绝时，先看错误：权限或认证问题交给 C 核对；非快进拒绝则先 fetch 并核对任务分支是否被其他人更新，与作者协调后合并远端任务分支。不用强推覆盖队友提交，不盲目重复推送。

### 5. 创建和更新 PR

在 GitHub 中选择本任务分支创建 PR，base 为 `main`。未接入真实接口或仍有阻塞时使用 Draft，写清依赖 PR。准备合入后按第五节请求对应成员复核。

PR 正文保留以下信息即可：

```text
解决的问题与实际行为：
改动范围：
依赖 PR / 契约 / 配置变化：
验证命令或操作步骤及结果：
未执行项、限制与剩余工作：
需要复核的成员：
```

界面或 3D 改动附必要的截图、短视频或操作说明，避免放入私密内容。合入后重新同步 `main`，下一个任务从新分支开始；不要在已 Squash 合入的旧任务分支继续叠加新任务。

## 八、多人协作如何避免环境冲突

**统一工具链和契约，每个人独立运行。** 不通过共享一个项目目录、一个数据库或一套 `node_modules` 来保持一致。

### 1. C 维护统一环境基线

下表约定环境基线的维护责任；当前版本与实际命令统一见 [运行说明](运行说明.md)。修改工具链或环境时同步更新该说明，并重新验证相关门禁。

| 项目 | 团队约定 |
| --- | --- |
| Node.js | 选定并验证具体版本，在 `.node-version` 记录；`package.json` 的兼容范围与之保持一致，CI 使用同一基线 |
| 包管理器 | 新工程使用 pnpm，`package.json` 的 `packageManager` 固定具体版本；不混用 npm、Yarn、Bun 生成其他锁文件 |
| 依赖 | 提交 `package.json` 与 `pnpm-lock.yaml`；成员首次安装和 CI 使用 `pnpm install --frozen-lockfile` |
| 运行与检查 | 记录实际安装、启动、类型检查、lint、测试、构建、迁移命令；不依赖个人别名或自动激活的环境 |
| 配置 | 提交不含密钥的 `.env.example`，列清必填项、用途和本地配置文件名，包括 `DATABASE_URL`、`TEST_DATABASE_URL`；成员各自填写，复制前检查目标文件是否已经存在 |
| 数据库 | 统一 PostgreSQL，主版本与服务端驱动由 C 维护；每人独立开发库、测试库及相应权限，CI 使用隔离 PostgreSQL 测试库 |
| 本地数据 | 上传与测试临时文件放在各自 checkout 内被忽略的目录；PostgreSQL 数据由各自的数据库服务持久化，开发、测试与生产数据库隔离 |
| Git 忽略与文本 | 配置 `.gitignore` 排除本地配置、数据、依赖与构建产物；`.gitattributes` 将代码和 Markdown 约定为 LF，保留明确需要其他格式的文件 |
| 环境验收 | 在干净 checkout 按说明复现安装、检查和构建；目标部署系统验证 PostgreSQL 连接、迁移与备份恢复，以及实际使用的原生依赖。记录实际测试过的系统，不把 Linux 通过写成 Windows 已验证 |

`--frozen-lockfile` 用于按已提交的锁文件安装；锁文件需要变化时会报错，不能把删锁文件或关闭冻结安装当作日常修复。[pnpm install 文档](https://pnpm.io/cli/install)

公共工程就绪后，各成员先核对：

```sh
node --version
pnpm --version
pnpm install --frozen-lockfile
pnpm run
```

前两项应与仓库版本要求一致；最后一项用于查看已定义脚本，再按运行说明执行对应检查和启动命令。缺少配置时补齐自己的本地配置，不把必填项改成静默默认值。

### 2. 独立目录、端口和数据

| 场景 | 做法 |
| --- | --- |
| 五人分别用自己的电脑 | 每人独立 clone、安装依赖、配置本地开发数据；不同电脑可以使用相同端口 |
| 同一台电脑上多人或多个已获授权的助手并行 | 每个并行任务独立 clone 或使用独立 worktree，分配不同分支、端口和可写数据目录；不在同一 checkout 并发切分支、改文件或暂存 |
| Windows、Linux 或 WSL 混合开发 | 各环境分别 checkout、安装依赖与构建；不复制或共用 `node_modules`、`.next`、PostgreSQL 数据目录或 Python 虚拟环境 |
| 使用共享磁盘或云同步目录 | 不把同一 checkout 作为多人实时工作区，不同步运行中的 PostgreSQL 数据目录和上传目录；通过 Git 交换源码 |
| 联调或生产环境 | 由 C 统筹部署与数据，成员通过接口联调，不让各自的本地程序同时写同一份部署数据库 |

启动服务前核对端口是否被占用。同机发生占用时，先确认进程归属，给自己的实例分配其他端口，不结束其他成员的服务。实际端口、配置名和停止方式以运行说明为准。

每人自己的数据库和上传目录只保存获准用于开发的素材。`DATABASE_URL` 与 `TEST_DATABASE_URL` 必须指向不同的 PostgreSQL 数据库，测试账号不得拥有开发、联调或生产数据库的写权限；不能以本地文件数据库替代真实 PostgreSQL 的事务和约束验证。自动化测试使用独立测试库与临时素材目录；破坏性测试不能指向个人开发数据、联调或生产数据。凭据通过团队认可的私密渠道配置，不放入 Git、PR、截图或问题日志。

### 3. 公共变更与冲突处理

- **依赖与锁文件**：先向 C 说明用途，由一位明确作者修改清单并生成锁文件，二者在同一 PR 提交。其他成员同步后按锁文件安装，不自行升级同一批依赖。
- **锁文件冲突**：先对齐最新 `main` 和双方的依赖意图，由 C 指定作者用固定 pnpm 版本重新生成所需结果并检查差异。不直接全选 ours/theirs，不删除锁文件后随机重装。
- **数据库迁移**：C 分配连续编号并协调合入顺序。新迁移在各自测试数据库验证；同步代码后按说明更新自己的开发库。编号冲突由作者与 C 解决，已应用迁移不重写，清库不作为默认修复。
- **环境变量**：新增配置时，同一个 PR 更新 `.env.example`、用途和本地迁移说明；只传字段要求，不传真实值，不覆盖队友的本地配置。
- **系统差异**：路径大小写与导入保持一致，不写个人绝对路径；项目脚本优先使用已有跨平台入口。确需 Bash 或系统工具时，写明执行环境与前置条件，不能默认 Windows 终端支持同一条命令。

### 4. 环境出问题时按这个顺序排查

1. 记录当前分支、提交、系统、Node.js 与 pnpm 版本，确认是否使用了不同工具链。
2. 确认已经同步依赖 PR，`package.json` 与锁文件一致；先解释冻结安装的报错，不删锁文件试运气。
3. 核对本地必填配置、端口、数据库和上传目录，以及是否误用了另一系统的依赖产物。
4. 核对 PostgreSQL 服务、连接配置、权限和迁移是否按当前代码版本落实；驱动或其他原生依赖安装失败时保留实际错误，由 C、D 对照目标系统处理，不关闭检查掩盖失败。
5. 仍无法定位时，由 C 协调在新的独立 checkout 复现。报告最小复现步骤、预期、实际结果和脱敏日志；保留原工作区和数据，不先清空整个项目。

环境变更解决后，把必要修正回到版本文件、锁文件、配置样例或运行说明中，不依赖某位成员口头传递一条特殊命令。
