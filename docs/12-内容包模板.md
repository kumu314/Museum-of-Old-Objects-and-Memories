# 用户输入、生成记录与测试内容包（E 主责）

> **依据**：`docs/PROJECT_PLAN.md` v0.7 §5.3 样例与模型、§9.5 分享与素材、§9.7 上传格式与限额、§6 AI 和故事如何配合；`docs/TEAM_EXECUTION_PLAN.md` §3.5 E 的最终责任与结束条件。
> **版本说明**：2026-10-24 改为方案 B 加照片生成模型。格式与限额统一见开发书 §9.7，本模板不重复定义；建模输入要求及资源预算按真实服务实测记录。此模板用于人工记录与验收，不表示新增字段已进入应用 schema 或现有 JSON 校验脚本。
> **硬约束**：内容缺失时**明确列出缺失项**，不由 AI 补造。不虚构演示故事、年份、人物关系与情绪；不确定处保留「约」「可能」「记不清」原话。

---

## 1. 一个内容包要装什么

一件展品 = 一个内容包。区分原始事实、生成与整理候选、用户确认及素材许可。普通用户通过界面提供材料并确认，E 维护获准测试内容和独立试用证据，不逐件代替用户录入或确认。原始来源保留，用户纠正时记录新版本，不由 AI 静默改写。

### 1.1 事实层（原始材料，只增不改）

| 字段 | 必填 | 说明 |
|---|---|---|
| 展品编号 | ✅ | 建议 `EX-01` 形式，全项目唯一 |
| 展品名称 | ✅ | 用物主自己的叫法，不用我们起的雅名 |
| 约略年代 | ✅ | 允许「八十年代末」「不记得哪年，小时候」。**禁止补成精确年份** |
| 类别 | ✅ | 支持范围内的旧物；注明样例、独立新输入或照片票据展示，生成支持范围以实测为准 |
| 原始讲述 | ✅ | 物主原话，逐字记录，不改写、不润色、不合并 |
| 讲述来源 | ✅ | 谁讲的、什么时候、通过什么渠道（当面/微信语音/文字） |
| 来源片段标识 | ✅ | 展签里每一句要能指回原始讲述的哪一段，用于 AI 草稿的来源标注 |
| 照片 | ✅ | 原图不裁剪、不压缩、不转格式；另存处理版 |
| 原声 | ⬜ | 可选。若提供，需单独标注许可范围 |
| 物主已知的疑点 | ⬜ | 物主自己说"记不清""可能是"的地方，**必须保留**，不能删 |

### 1.2 整理层（草稿，可迭代）

| 字段 | 必填 | 说明 |
|---|---|---|
| AI 草稿 | ⬜ | 由 AI 生成，必须带来源片段标识；生成时间与所用模型记下 |
| 人工修改记录 | ⬜ | 谁改了什么，为什么改。改掉事实性内容要写理由 |
| 追问清单 | ⬜ | 最多两个待问物主的问题（§6 限制） |
| 当前展签 | ✅ | 待确认的最终文本。事实与整理必须可区分，读者能看出哪句是原话 |

### 1.3 确认层（版本记录，不可变）

| 字段 | 必填 | 说明 |
|---|---|---|
| 确认版本号 | ✅ | 对应当前展品版本，包含所采纳模型、展签及展示素材；公开内容修改或采纳新模型后失效 |
| 确认人 | ✅ | 当前用户明确操作；不是物主或权利人时另记录相应授权，E 不代替用户确认 |
| 确认时间与渠道 | ✅ | 例：10 月 24 日 20:15 微信语音 |
| 确认范围 | ✅ | 采纳的模型版本、展签、展示图片和原声，生成完成不自动确认或发布 |
| 分享范围 | ✅ | 默认私有草稿，由用户明确发布。期望“仅限家人”是用途记录，当前持链接访问不等于指定家人账号鉴权 |

### 1.4 素材许可（每个文件单独记）

| 字段 | 说明 |
|---|---|
| 文件标识 | 文件名或哈希，确保能对上具体文件 |
| 来源 | 物主提供 / 公共馆藏（如 Smithsonian CC0）/ 开源模型库 |
| 许可范围 | 第三方建模 / 演示 / 持链接分享 / 仅内部验收分别记录，不相互推定 |
| 授权人 | 谁给的许可，什么时候 |
| 近似程度 | 区分真实生成、内置及人工制作，标明未拍摄背面和细节的推测，不称为精确复原 |

### 1.5 模型生成记录

| 字段 | 说明 |
| --- | --- |
| 用户、展馆和展品 | 用内部标识关联，公开材料不暴露私有账号或任务信息 |
| 输入 | 照片资产 ID、文件哈希及来源版本，记录实际使用照片；不能只留可变文件名 |
| 任务 | 本地任务及外部任务标识、服务和模型版本、提交与完成时间；凭据不进入记录 |
| 输出 | 生成模型资产 ID 和版本、格式、字节数、纹理与几何体预算检查、预览结果 |
| 状态与成本 | 真实耗时、费用、失败原因和是否为显式新一轮生成；未知时如实标明 |
| 采纳 | 用户采纳的模型与展品版本，旧结果或未采纳结果不得自动替换内容 |

原始照片私有保存，发送第三方服务及对外展示使用的图片均按开发书处理敏感元数据。照片薄片、预置资产与实时生成分开标明，不能混记为成功生成。

## 3. 样例与独立输入缺口

现有仓库已记录相机、磁带、车票演示模型来源；这不代表真实物主内容包或自动建模已经通过验收。六格、三件样例与至少一件获准原声沿用，最终素材完整性在验收清单登记。

| 输入 | 需要什么 | 当前证据或缺口 |
| --- | --- | --- |
| 三件完整样例 | 照片、原始讲述、展签、模型或明确展示方式、授权和用户确认 | 演示模型已存在，完整真实内容包尚未验收 |
| 独立新照片 | 支持类别的新旧物照片，区别于内置演示资产 | 待 D 确定输入要求、E 收集获准照片并走真实生成 |
| 原声 | 至少一件可播放的获准录音，记录公开用途 | 完整内容及实际浏览器、手机播放待验收 |
| 质量和失败输入 | 缺失、模糊、反光、遮挡、信息矛盾或不确定等 | E 与 D 按实际支持范围设计，不虚构服务能力 |

不提前规定未经验证的“6 至 10 张”等照片张数，也不以现成模型代替独立输入的自动建模验收。服务支持范围、照片数量与拍摄要求一经实测确定，补充到开发书和面向用户的指引。

## 4. E 持续推进的任务

| 事项 | 依赖 | 交付与证据 |
| --- | --- | --- |
| 核对素材用途和权利 | 获准内容与实际权利人 | 第三方建模、演示、分享、内部测试的对应记录 |
| 整理样例与独立新输入 | D 的输入要求，A 的展示规范 | 内容包、生成记录、缺失项与拍摄指引 |
| 组织普通用户独立试用 | B、C、D、A 的可运行流程 | 账号接入、上传、真实生成、预览确认、发布与参观步骤，不由队员代做 |
| 检查事实和生成质量 | 原始来源、真实模型和展签 | 近似程度、不确定性、错误与用户反馈 |
| 执行完整验收并跟进复测 | 验收清单和各作者修复 | 两用户隔离、任务恢复、撤销分享、电脑手机与恢复演练结果 |
| 整理最终材料 | 真实产品和验收证据 | 操作说明、来源、成本、实际限制与简短视频 |

以上均为持续责任，状态统一记录在验收清单，避免多份进度表互相冲突。现有 `scripts/content/check-content-pack.mjs` 及 JSON fixture 只校验已有字段；新增模型任务和用户归属的应用契约及自动检查由对应作者按任务补齐，模板不能代替运行校验。
