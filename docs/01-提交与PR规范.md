# 提交与 PR 规范（含 AI Agent 条款）

> 为什么单独写这一份：我们的队伍实际上不止几个人——还有若干 AI Agent。
> AI 可以在 10 分钟内产出 800 行代码，但它**不会替你判断这 800 行该不该存在**。
> 这份规范的目的不是限制产出，而是**让"看起来很多"和"真的有用"能被区分开**。
>
> **这份规范与选题无关**，换选题不需要改。

---

## 一、别人已经踩过的坑（我们不必重踩）

AI 生成的低价值提交已经是开源社区的公开危机，不是我们独有的担心：

| 项目 | 做法 | 结果 |
|---|---|---|
| **Apache 基金会** | 建议在提交信息里加 `Generated-by:` 标签披露 AI 使用 | 仅解决许可问题，不解决质量 |
| **OpenInfra 基金会** | 用 `Generated-By:` / `Assisted-By:` 标签，并要求**把 AI 代码当"不可信来源"加强审查** | 目前最接近我们需要的做法 |
| **Ghostty** | 2025/08 强制披露 → 2026/01 升级为**零容忍**（AI 贡献仅限已被接受的问题） | 披露没起作用 |
| **tldraw** | 自动关闭**所有**外部 PR | 最激烈，直接停掉开放贡献 |
| **cURL** | 连续 6 年、8.6 万美元的漏洞赏金计划被 AI Slop 拖垮，2026/01 终止 | 20% 提交是 AI Slop，仅 5% 识别出真漏洞 |
| **Gentoo / NetBSD** | 全面禁止 AI 生成代码（NetBSD 将其归为"tainted"） | 靠禁令，但承认"一两年后检测将几乎不可能" |

> 来源：RedMonk《AI Slopageddon and the OSS Maintainers' Burden》（2026-02），经 36 氪《AI 正在毁掉开源》编译（2026-03-30）。

**我们从中拿走的三条**（而不是照抄禁令）：

1. **披露是低成本、高收益的**——加一行 trailer 就能让审查者知道该多看一眼。
2. **"必须能解释自己提交的内容"才是真正的过滤器**——Ghostty 的原话是"我们不反对 AI，我们反对愚蠢"。
3. **禁令在小队里没有意义**——我们本来就要用 AI。有效的是**机械门禁 + 人工解释**。

---

## 二、三条原则

| 原则 | 具体含义 | 违反的后果 |
|---|---|---|
| **可披露** | 用了 AI 就写一行 `Generated-by:`，不丢人 | 答辩被问"这行谁写的"答不上来 |
| **可解释** | 提交里的每一行，作者都要能讲清为什么这么写 | 无法回滚、无法修 bug、无法答辩 |
| **可验证** | PR 必须带"我怎么知道它是对的" | 合进去的东西没人敢动 |

## 三、Commit 规范

### 格式

```
<type>(<scope>): <做了什么>

<可选：为什么这么做 / 有什么取舍>

Generated-by: <工具名>        ← 用了 AI 才写，纯手写不用写
```

**type 只能取这几个**（CI 会检查）：

| type | 什么时候用 |
|---|---|
| `feat` | 新增功能 |
| `fix` | 修 bug |
| `docs` | 只改文档 |
| `refactor` | 不改行为的重构 |
| `test` | 只改测试 |
| `chore` | 构建/依赖/配置 |
| `style` | 纯格式（**单独成提交，别混在功能里**） |
| `perf` | 性能 |

### 好 / 坏对照

| ✅ 能过 | ❌ 会被拦 |
|---|---|
| `feat: 登录页支持手机号验证码` | `update` |
| `fix: 修复分页在第 2 页重复首条的问题` | `修改一下` |
| `docs: 补充部署到 Vercel 的步骤` | `提交代码` |
| `refactor: 把请求逻辑从页面抽到 lib/api.ts` | `优化` |
| `chore: 升级 next 到 14.2` | `fix bug` |

**判据很简单**：把这条 message 单独发给队友，他能不能知道**改了什么**。答不上来就是垃圾提交。

### 一个提交 = 一件事

- 改了样式 + 改了接口 → **拆成两个提交**。理由不是洁癖，是**回滚时你只想撤一个**。
- 单次提交**新增 ≤ 500 行**（不含 lock 文件和生成物；**删除行不计**，清理类提交不该被拦）。超了说明你在做两件事以上。
- 不确定要不要拆时问自己：**"如果这行出问题，我能不能只回滚它？"**

## 四、明令禁止的 8 类提交

前 6 类**已做成自动拦截**（见第六节），后 2 类靠人判。

| # | 类型 | 例子 | 自动拦 |
|---|---|---|---|
| 1 | 空壳文件 | 新建 `lib/api.ts` 里面只有 `// TODO` | ✅ |
| 2 | 调试残留 | 提交里带 `console.log('aaa')`、`debugger` | ✅ |
| 3 | 大文件 | 提交 3MB 的图片/视频/数据集 | ✅ |
| 4 | 敏感文件 | `.env`、`*.pem`、密钥、真实用户数据 | ✅ |
| 5 | 生成物 | `node_modules/`、`.next/`、`dist/` | ✅ |
| 6 | 巨型提交 | 单次新增 > 500 行 | ✅ |
| 7 | 全量格式化 | 只因为"跑了一下 prettier"导致 30 个文件全变 | 人判 |
| 8 | "以后会用"的代码 | 写了没被调用的函数、留着的注释代码块 | 人判 |

**第 7 类特别说明**：格式化本身没错，错的是**混在功能提交里**。要格式化就单独提一个 `style:` 提交，让它在历史里一眼可辨。

## 五、PR 规范

模板已配好（`.github/pull_request_template.md`），必须填满三块：

1. **改了什么**（一句话）
2. **怎么验证的**（命令输出 / 点了哪个页面 / 手机试过没有）
3. **有没有影响别人**（改了共享模块、数据结构、配置就必须写）

### 一条硬规则：PR 描述必须由人写

**不能让 AI 代写"改了什么"。** 理由：
- 这段文字是**唯一能证明你读过自己代码**的东西。
- AI 写的"改了什么"读起来永远通顺，所以它**永远不能证明任何事**。

允许 AI 帮你润色措辞，但**内容必须来自你**。

## 六、机械门禁（已配好，装一次即可）

### 安装

```bash
bash scripts/install-hooks.sh
```

它做两件事：把 `core.hooksPath` 指向 `.githooks/`，并给钩子加执行权限。**每个队友克隆后跑一次。**

### 提交时拦什么

| 检查 | 位置 | 触发后 |
|---|---|---|
| message 格式 / 空泛词 / 长度 | `commit-msg` | 拒绝提交，提示怎么改 |
| 空壳文件（≤2 行且只有 TODO） | `pre-commit` | 拒绝 |
| `console.log` / `debugger`（仅源码目录） | `pre-commit` | 拒绝 |
| 单文件 > 1MB | `pre-commit` | 拒绝 |
| 敏感文件 / 生成物目录 | `pre-commit` | 拒绝 |
| 单次新增 > 500 行 | `pre-commit` | 拒绝，提示拆分 |

> `scripts/`、`tools/` 下的 `console.log` **不会被拦**——命令行工具本来就该打印东西。误伤比漏网更烦人。

### 想跳过怎么办

```bash
git commit --no-verify
```

**允许用，但有代价**：用完必须在群里说一句"我跳过了钩子，原因是 X"。
钩子是提醒不是法律，但**跳过要留痕**——这是唯一的要求。

### CI（推上去之后还会再查一遍）

`.github/workflows/ci.yml` 会在每次 push / PR 时跑：

1. `node scripts/scan-noise.mjs`（扫全仓库噪声）
2. 每条 commit message 格式检查

> 选题定下、有了测试之后，**第一步要往 CI 里加的是你自己的测试命令**。

**本地钩子可以被 `--no-verify` 绕过，CI 绕不过。** 这是第二道闸。

## 七、AI Agent 专用条款

这三条是给"我们自己用 AI"定的，不是给外人。

### 7.1 披露

用了 AI 就在 commit body 末尾加一行：

```
Generated-by: Claude Code
```

工具名写真实的（Claude Code / Cursor / Copilot / Codex…）。**这一行不扣分，反而说明你有意识。** 参照 Apache 与 OpenInfra 的通行做法。

### 7.2 三条禁令

| 禁令 | 为什么 |
|---|---|
| **不提交没跑过的代码** | AI 生成的代码"看起来能跑"和"真的能跑"是两件事。跑一次成本 30 秒 |
| **不提交解释不了的行** | 答辩时评委指着任意一行问"这是干嘛的"，你答不上来就全盘失信 |
| **不提交"以后会用"的东西** | 没人调用的函数不是资产，是负债——它会被当成"已完成" |

### 7.3 交付前的硬门（比赛结束前必须做）

**每人随机抽自己模块里的 5 行，讲给另一个队友听。** 讲不清就去读，读完再讲。

这条不是形式主义。它是**唯一能在有限时间里验证"你真的拥有这份代码"的方法**，也是答辩现场唯一救命的准备。

## 八、互查：几个人怎么低成本审

不要搞 code review 流程，时间撑不住。用**轮转 5 分钟**：

| 时机 | 做什么 |
|---|---|
| 每天 21:00 站会后 | 每人花 5 分钟看**另一个人**昨天合进 main 的提交 |
| 看什么 | 只看两件事：① message 说得清吗 ② 有没有调试残留 / 空壳文件 |
| 发现问题 | 直接在群里说，不改代码，让对方自己改 |

**为什么只查这两件**：这两件是"客观可判"的。查逻辑对错成本太高，会变成吵架。

## 九、出问题了怎么收拾

| 情况 | 做法 |
|---|---|
| 刚提交、还没 push | `git commit --amend` 或 `git reset --soft HEAD~1` |
| 已 push、只有自己在这分支 | `git push --force-with-lease`（**不要用 `--force`**） |
| 已合进 main、别人已经拉了 | **不要改写历史**，提一个 `revert: xxx` 提交 |
| 不小心提交了 `.env` | 立刻换密钥，再清理历史。**只删文件不够**——它已经在历史里了 |

> `--force-with-lease` 比 `--force` 安全：如果远端在你 push 前被别人更新过，它会拒绝而不是覆盖。
