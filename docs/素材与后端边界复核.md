# 素材与后端边界复核（C 侧）

更新：2026-10-24。范围：素材上传的体积边界、事务与私有文件清理的失败路径、用户隔离的现状。

**本次未改动数据库结构、权限模型或接口契约。** 所有修复都在既有的 `readAssetUpload`、清理判定与测试脚本内。

## 1. 超限回归的准确顺序

实测环境：Windows 11 / Node 26.12.0 / Next 16.4.3（dev + webpack）/ pnpm 12 hoisted。

`tests/e2e/assets-http.test.ts` 的请求序列，服务端日志逐条对应：

```
POST /api/museums/{id}/assets  201   正常上传（图片）
POST /api/museums/{id}/assets  413   A：图 10 MiB + 1 字节
POST /api/museums/{id}/assets  201
POST /api/museums/{id}/assets  201
POST /api/museums/{id}/assets  413   A'：音频 20 MiB + 1 字节
POST /api/museums/{id}/assets  201   替换素材
POST /api/museums/{id}/assets  201   跨馆素材
GET  /api/museums/{id}/assets/{assetId}  401 / 404 / 200 / 200（访问控制与变体）
POST /api/museums/{id}/assets  201   恰好等于图片上限
POST /api/museums/{id}/assets  413   B：图片上限 + 1（流式累加拒绝）
POST /api/museums/{id}/assets  413   C：20 MiB 裸包，content-length 直接拒
GET  /api/museums/{id}         200   读馆成功
GET  /api/museums/{id}         200   再读一次取版本号
--- POST /api/museums/{id}/exhibits  从未到达服务端 ---
DELETE /api/museums/{id}       200   直接进入 finally 清理
```

失败形态固定在 `POST .../exhibits`：`TypeError: fetch failed`，`cause: Error: read ECONNRESET`（errno -4077，syscall `read`）。

三点必须说清楚：

1. **是 C 那条 413 造成连接污染，不是 A、A'、B。** 前三条都在读流的过程中被拒，流已被消费；C 由 `content-length` 预判，请求体一个字节都没读。
2. **413 这条响应本身是正确的**：状态码、`no-store`、`nosniff`、错误码断言全部通过。坏的是传输层连接状态。
3. 中间两次 GET 能成功，说明连接池里还有别的干净连接；出问题的是被 413 污染的那一条。所以现象表现为"偶发"，实际是确定的连接复用顺序问题。

创建展品是**非幂等**操作，不能用重试掩盖。回归里保留原有 413 断言与完整场景顺序，未跳过、未加重试。

## 2. 根因

`readAssetUpload` 用 `content-length` 预判超限，直接抛 413。此时请求体完全未读，Node 返回响应后这条连接上仍挂着未消费的请求字节。undici 把它放回连接池，下一个请求复用时撞上残留数据 → RST。

## 3. 修复

### 3.1 `src/server/core/assets.ts`：把请求体读空再拒绝

- `content-length` 超限不再立即抛错，改为**读空请求体后**再抛 413；只丢弃、不累积（超限时立即 `chunks.length = 0` 释放已存字节）。
- 流式累加超限同样继续丢弃。
- 丢弃阶段有**两条硬边界**，任一触顶即停止：总量 `drainCeiling = 2 × multipartLimit`；单次读取超时 `drainTimeoutMs = 5s`（客户端停传时 `read()` 永不返回，不设边界会把 handler 挂死）。
- 只要「已判定超限、且没读到流结束」（超时、超量、读取异常），就 `await reader.cancel()` **主动终止这条流**，而不是把读锁还回去就算了——残留数据留在连接上，下一个请求复用它就会读到半截请求。
- 正常读完（`done`）不取消：连接本身已经干净，取消是多余动作。

### 3.2 试过但否决的做法

在 413 响应上加 `Connection: close`。实测 Next 16 dev server 下响应会变成不完整，客户端报：

```
HTTPParserError: Response does not match the HTTP/1.1 protocol (Invalid EOF state)
```

比原问题更糟，已回退。

### 3.3 评审反馈补上的两处缺口

第一版「读空再拒」只解决了"体量大但正常发完"的场景，被评审指出两个真实缺陷，均已修复并补了回归：

| 缺口 | 现象 | 修法 |
|---|---|---|
| 丢弃阶段没有时间上限 | 客户端停传后 `read()` 永不返回，主线已返回 413 而请求仍挂着 | 丢弃阶段单次读取加 `drainTimeoutMs = 5s`，超时按「停止」处理 |
| 触顶后只 `break` + `releaseLock` | 请求体仍未处理完，返回 413 后流仍可读，仍有复用风险 | 触顶时 `reader.cancel()` 强制终止，不等对端发完 |
| 普通上传阶段吞掉读流错误 | 把「异常」当成「正常结束」，已收集的片段被当作完整文件解析入库——截断的上传变成合法素材 | 普通阶段的 `read()` **不 catch**，错误原样抛出、拒绝整次上传；只有丢弃阶段才把异常归为「停止」 |
| 测试把探测超时算作通过 | 一直挂起（既不结束也不报错）的流也能通过断言 | 断言收紧为「必须是结束或报错」，`timeout` 判失败 |

对应回归在 `tests/server/upload-boundary.test.ts`（7 例）：停传到时间上限即返回、超量立刻终止、正常读完不取消、流式累加超限同样终止、未超限上传不受影响、**普通上传阶段读流报错必须整次拒绝**，以及**「413 之后请求体必须结束或报错」**——后者直接钉住第二处缺口的反面：拒绝后从这个请求体探测不到任何字节，能读出来就说明残留数据可被下一个请求吃掉。另有一条用例确认 413 之后紧接的正常上传仍可正常解析。

### 3.4 `scripts/test-http.ts`：修复被掩盖的失败原因

`stopServer()` 用 `process.kill(-pid)` 结束进程组，Windows 没有这个语义，收尾时抛 `kill ESRCH` 直接终止脚本，把真正的测试失败盖住。改为 Windows 下直接结束子进程，`ESRCH` 视为已退出。

## 4. 故障注入三项

把清理判定从 `catch` 里抽成纯函数 `cleanupAllowed`（`src/server/assets/storage.ts`），规则只有一条：**只有确定没提交才允许删文件**。

| 场景 | 状态（begun / commitAttempted / rollbackConfirmed） | 允许清理 | 结果 |
|---|---|---|---|
| 文件写完、事务未开始 | false / false / false | 是 | 不误留孤儿 |
| 事务内失败、回滚已确认 | true / false / true | 是 | 不误留孤儿 |
| 事务内失败、回滚未确认 | true / false / false | **否** | 保守保留 |
| **COMMIT 已发出、结果未知** | true / true / false | **否** | 不删可能已提交的文件 |
| COMMIT 后又声称回滚成功 | true / true / true | **否** | 同上，COMMIT 标记优先 |
| **提交成功但响应失败** | 不进 catch 分支 | — | 文件保留 |
| 未开事务却声称 COMMIT 过 | false / true / false | **否** | 保守保留 |

清理侧（`cleanupUncommittedAsset`）另有五道保护，均已有用例覆盖：

- 事务状态不是 `not-started` / `rolled-back` → 直接抛错，不靠调用方自觉
- 引用查询失败 → 抛错并保留文件
- 仍有 `assets` 行或 `snapshot_assets` 引用 → 保留
- 存储键首段与资产 id 不一致 → 抛错，不据此删目录
- 只删 `uploadDir/<id>/`：同目录的其他资产与旧素材不受影响

**覆盖层级如实说明**：以上是单元级验证（`tests/server/assets.test.ts` 的清理判定与目录隔离用例）。请求体丢弃的时间/体积边界另由 `tests/server/upload-boundary.test.ts` 覆盖。端到端只覆盖正常路径与超限路径。"COMMIT 结果未知"无法在真实数据库上稳定注入（需要让 `COMMIT` 在服务端已提交后仍向客户端报错），因此靠纯函数与清理契约保证，**不宣称做过端到端注入**。

## 5. 用户隔离的边界（重要）

本节最初记录的是**归属迁移之前**的单账号状态。归属隔离与账号接入已在 `feat/user-ownership-and-registration` 落地：`museumRecord` 必须带 actorId，他人展馆与不存在的展馆返回同一个 `NOT_FOUND`，列表只返回本人展馆；普通用户通过 `POST /api/auth/register` 自助注册。`test:http` 因此从单账号扩到双账号并新增两个用例文件。

本次补查落实参观也须登录：分享数据与素材 API 在读取 token 和快照前验证有效会话，业务层也要求有效账号；已登录的非所有者可持有效链接参观。匿名请求、退出后的旧 cookie 均不能读取内容。注册即登录同时撤销被替换的旧会话，注册计数清理与账号/会话写入处于同一事务。

当前证据分层如下，不能互相替代：

| 层级 | 证据 | 能证明什么 |
|---|---|---|
| 实库双账号 | `tests/db/ownership.test.ts`（4 例） | 列表、读取、改名、删除、加展品、素材、AI 采纳、发布、换链、停止分享全部按归属拒绝；归属不可更改 |
| HTTP 双账号 | `tests/e2e/ownership-http.test.ts` | 直接构造 ID 的读、改名、删除、加展品、发布、换链、取素材、传素材全部 404，且与不存在展馆的响应逐字段相同；越权后无副作用 |
| HTTP 注册 | `tests/e2e/registration-http.test.ts` | 校验规则、用户名唯一性、注册即登录、重新登录、注册账号之间的归属隔离；登录与注册的节流计数器互不影响 |
| 浏览器端到端 | 未执行 | `E2E-B2` 仍是"部分执行"，服务端隔离通过不代表浏览器流程通过 |

## 5.1 节流计数器必须按用途分区

评审复现过一条真实缺陷：注册节流原先用字符串拼接做命名空间（`'register:' + username`），而用户名允许包含冒号。于是名为 `register:alice` 的账号，其登录键与名为 `alice` 的注册键是同一个字符串——任何人反复注册 `alice` 十次，就能让 `register:alice` 的持有者无法登录五分钟。

修法不是把分隔符换成"更不可能出现的字符"。只要键是拼接出来的，冲突就取决于用户名的字符集假设，而字符集假设会随产品需求变化。`migrations/0004_login_attempt_scope.sql` 把用途放回独立的列，主键改为 `(scope, username)`，让数据库约束而不是约定来保证两组计数器不相交。

同时修正了成功登录时的清理范围：原来按 `username` 删，会把同名账号的注册计数一起清掉。现在只删自己的那一行。

回归 `tests/e2e/registration-http.test.ts` 的第二例钉住两点：受害账号密码正确时必须能登录；注册被节流后，同名账号的登录也必须照旧可用。后者针对的是把两种用途合并成一个计数器的做法——那等于把"用注册接口打满别人登录额度"变成一个公开可用的拒绝服务手段。


仍有两条不能宣称已完成：

- **持久化生成任务的归属尚未实现**，因为任务本身还不存在。B02 里"任务及结果不越权"要等任务表落地后补用例。
- **浏览器与设备端未验收**。注册/登录界面由 B 负责，E2E-B2 与 DEV-1/DEV-2 需要真实浏览器与实际手机，服务端用例不能替代。

结论：可以说"服务端已实现用户名+密码自助注册并按账号隔离展馆、展品与素材"，**不得**说"E2E-B2 通过"或"完整自助流程已验收"。

| `pnpm build` | 通过 | 通过 |

`pnpm test:http` 的 2/2 只是在 Windows 上证明不再复现 ECONNRESET；评审方在隔离的流边界上复现的两处缺口由新增的 `tests/server/upload-boundary.test.ts` 直接覆盖（停传、超量、读完、流式超限、未超限五条）。

顺带修掉的假失败：`tests/server/assets.test.ts` 的符号链接逃逸用例在 Windows 上一直红。原因是 `fs.symlinkSync(dir, path)` 不传 type 时建出来的是普通空目录——`lstat` 不是符号链接、`realpath` 不解析，守卫自然测不到。改用 `'junction'` 后正常（PR #4 已从 `outsidePublic` 的跨盘判断侧另行加固）。这属测试夹具可移植性，**不是守卫有缺口**。

## 7. 复现命令（脱敏）

```bash
# 依赖与数据库
pnpm install --force          # 切到 hoisted 布局后必须 force，否则只回 Already up to date
pnpm db:local                 # 15432 / 15433
pnpm db:migrate && pnpm db:migrate:test

# 回归
pnpm test                     # 契约 + 服务端单元
pnpm test:db                  # 真实 PostgreSQL 事务与归属
pnpm test:http                # 自带临时库与独立 server
```

`pnpm test:http` 每次创建一次性数据库 `http_test_<uuid>` 与临时上传目录，结束时清理；服务端日志在 `.local/http-regression-<id>/server.log`。

日志只含路由、状态码、耗时，不含请求体、文件名、连接串。业务错误日志是单行 JSON（`category` + `assetId`），不含凭证与物理路径。
