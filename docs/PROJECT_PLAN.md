## 1. 我们要做什么

我们希望把旧物和它背后的故事，做成一座可以打开、观看和分享的数字收藏柜。

用户看到的不是一张文件列表，而是一座有格位、有灯光、有物品纵深的 3D 展柜。点击一件旧物，可以把它取出、旋转查看，同时阅读物主的讲述、查看实拍照片、播放原声。

产品的价值来自三件事：

- 把散落的照片、录音和记忆整理成完整内容。
- 用展柜和检视动作，让旧物值得被停下来观看。
- 把结果交付给另一个人，使其能通过链接参观。

首版先围绕“为家人制作一份旧物纪念展”展开。这个场景仍是需要验证的产品假设，不能直接当作已经成立的市场需求。

## 2. 谁会使用它

项目中需要区分四种角色。实际使用时，一个人可能同时承担多种角色。

| 角色 | 关心的问题 |
| --- | --- |
| 客户 | 能否得到一份适合送给家人或自己保存的纪念作品 |
| 物主 | 故事是否准确，哪些内容可以展示 |
| 制作者 | 能否顺利收录素材、整理内容、制作并交付 |
| 参观者 | 能否方便打开、看懂故事、查看物品和播放原声 |

首版需要验证的主要问题是：

1. 对方是否愿意提供旧物照片和讲述。
2. 整理后的故事是否让物主感到准确。
3. 展柜是否让参观者愿意继续打开下一件旧物。
4. 最终结果是否值得保存、分享或付费制作。

“觉得有意思”与“愿意付款”是不同的信号，记录反馈时需要分开。

## 3. 两种制作模式

### 3.1 方案 A：团队协助制作

客户提供照片、录音和讲述，团队使用工作台完成建馆，物主确认故事后，由团队发布并交付参观链接。

流程：

**客户提出需求 → 提供素材 → 团队收录与整理 → 物主确认 → 团队发布 → 客户和家人参观**

这种模式首先验证的是：团队能否完成一次有价值、可重复的纪念展制作服务。

### 3.2 方案 B：用户自助建馆

用户进入产品后，自己创建展馆、上传素材、整理故事、确认内容并发布。

流程：

**用户进入制作入口 → 创建展馆 → 收录旧物 → AI 辅助整理 → 自行确认 → 发布并分享**

这种模式首先验证的是：普通用户能否在没有团队陪同的情况下完成制作。

### 3.3 比较与取舍

| 比较项 | 团队协助制作 | 用户自助建馆 |
| --- | --- | --- |
| 客户投入 | 提供素材、补充故事、确认内容 | 需要自行理解并完成制作流程 |
| 核心界面 | 团队工作台和参观页面 | 新手引导、用户工作台和参观页面 |
| 身份与权限 | 受保护的团队制作入口 | 用户身份、个人展馆归属和用户间隔离 |
| 故事质量 | 团队可以帮助追问和修订 | 需要界面帮助用户判断和补充 |
| 模型处理 | 团队预先制作或选择模型 | 需要明确告诉用户哪些物品能够呈现 |
| 比赛中的主要证明 | 能完成一次真实服务和交付 | 用户能够独立完成建馆 |
| 后续收费假设 | 按展馆或制作服务收费 | 按模板、容量或增值能力收费 |
| 主要风险 | 人工成本高，交付效率需要验证 | 开发范围大，用户容易在制作中途放弃 |

首版采用方案 A。方案 B 保留作取舍背景，不进入本轮实现与验收，也不建立双模式框架。

## 4. 首版做什么

首版围绕一条完整流程组织功能：

**收录旧物 → 保存素材与讲述 → AI 整理 → 人工确认 → 发布 → 他人参观**

### 4.1 共同必须完成的能力

| 能力 | 首版内容 | 完成标准 |
| --- | --- | --- |
| 旧物收录 | 名称、约略年代、照片、原始讲述，可附原声 | 保存后刷新仍可恢复 |
| 故事整理 | AI 根据已有讲述生成展签草稿与必要追问 | 至少一次真实调用成功，失败不丢失输入 |
| 人工确认 | 审阅、修改并明确确认展签 | 影响公开内容的修改会使旧确认失效 |
| 3D 展柜 | 有真实空间层次的柜体和格位 | 样例可以正常陈列与选中 |
| 重点检视 | 取出、旋转、缩放、放回 | 快速操作后物体与镜头仍能恢复 |
| 故事面板 | 展签、实拍照片、年代、原声 | 内容与当前选中展品一致 |
| 发布分享 | 发布当前确认内容，生成参观链接 | 另一浏览器可以打开 |
| 停止分享 | 停止访问或更换链接 | 旧链接的数据及私有素材新请求均失效 |
| 持久保存 | 保存展馆、素材与发布版本 | 重启服务后仍可读取 |
| 失败处理 | AI、模型或网络失败时给出明确状态 | 用户可以继续编辑或查看已有内容 |

展签指随展品展示的短文。原始讲述、AI 草稿和已确认展签需要保持清楚的区别。上传格式、大小和尺寸统一使用第 9.7 节的取值，错误反馈统一使用第 9.8 节的契约。

### 4.2 方案 A 的必需项

- 完成真实的团队登录、内部工作台和服务端权限校验。首版按单团队、预置成员账号、相同制作权限组织，具体认证机制由 C 根据部署环境落实。
- 物主通过线下或已有沟通渠道确认具体版本，E 维护对应记录，制作人员执行系统内的确认操作。公开内容变化后重新确认。
- 客户无需制作账号；首版不另建客户注册、客户编辑后台、物主审批账号或多租户系统。

这些能力不能因为比赛时间紧而只在前端模拟。

### 4.3 有余力再做

- 重点展品上的细节热点。
- 自动语音转文字。
- 浏览器直接录音。
- 二维码或图文导出。
- 更多展品与额外视觉主题。

每次只增加一项，并确认共同必需能力已经通过验收。自动转写未进入首版前，不把它的实现和测试设为必需门禁。

### 4.4 首版不做

大型展厅漫游、多人实时参观、社区、交易、支付系统、多级组织权限，以及任意旧物的自动精确三维重建。

增加需求时，需要说明它替换哪项现有工作。

新增的公开展馆、社交发现、自传和共同记忆等想法统一记录在第 12 节，收费方向见第 11.1 节；目前作为后续产品方向，不自动纳入首版实现与验收。

## 5. 用户会看到什么

### 5.1 展柜

建议首版采用两行三列的六格展柜，准备三件完整样例，留下继续收录的位置。

视觉方向采用偏暗背景、暖色格内灯光和清楚的铭牌。柜内显示名称和简短年代，完整故事在选中后展开。

参考收藏柜的陈列与检视方式，柜体、材质和界面使用自己的设计。

### 5.2 检视

点击展品后，物品从格位中取出，进入适合观察的位置。用户可以旋转和缩放，通过返回按钮或 Esc 放回。

交互分为四个状态：

`overview → focusing → inspecting → returning → overview`

需要重点检查：

- 连续点击不会重复取出同一物品。
- 拖拽旋转只影响当前展品。
- 返回后柜体、物品和镜头位置正确。
- 切换展品时，上一段音频停止。
- 音频由用户主动播放。
- 手机有明确的选择和返回入口。

模型初始变换、包围盒适配与恢复目标遵循第 9.6 节。恢复不能依赖被打断时的动画位置。

### 5.3 样例与模型

建议选择一件重点立体展品、一件简单立体展品、一件照片或票据类展品。相机、磁带、车票可以作为候选，最终以可取得、获准使用的素材为准。

- 重点展品打磨轮廓、材质和可见痕迹。
- 普通展品使用简单模型或实拍贴图。
- 照片与票据可以使用有厚度的薄片。
- 所有展品保留实拍入口。
- 对近似模型明确标注，不把未提供的背面和细节称为精确复原。

模型加载失败时显示实拍与重试入口；WebGL 不可用或运行期间上下文丢失时提供明确状态和图文参观入口。桌面比赛主流程仍需要完成真实 3D 展示与检视。

## 6. AI 和故事如何配合

AI 的职责是整理物主已经提供的内容，帮助表达和追问。

输入包括旧物名称、约略年代及带有来源标识的讲述片段。输出包括：

- 一段建议为 60 至 120 字的展签草稿。
- 最多两个追问，也可以没有。
- 关键内容对应的来源片段标识。

不得补造人物、年份、关系、事件和情绪。原文中的“约”“可能”“记不清”需要保留。

AI 输出先经过结构校验，再交给人审阅。来源标识有效只能证明结构正确，不能证明内容一定真实。

方案 A 中，物主需要确认具体版本的故事，E 核对并记录反馈，制作者再执行系统内的确认操作。首版不建设独立的多人审批流程。

AI 超时或不可用时，保留已保存的素材与讲述，允许人工整理继续交付。测试样例与预先录制的结果必须明确标识。

## 7. 五类职责怎样协作

A 为 Codex（用户本人），B—E 的具体姓名和可投入程度在开工时登记。详细任务和目录归属见 [团队执行方案](TEAM_EXECUTION_PLAN.md)；每个交付包有一名最终负责人，参与者对自己的模块负责。

| 主责 | 主要工作 | 交付物 |
| --- | --- | --- |
| A：产品与 3D | 产品取舍、柜体、模型、检视与镜头 | 可操作的展柜和产品演示主线 |
| B：工作台与故事界面 | 收录、编辑、确认、发布界面及参观页 | 完整制作界面与故事、音频联动 |
| C：核心业务与工程集成 | 契约、数据、权限、发布、集成、部署与恢复 | 可验证业务链路与可运行部署版本 |
| D：AI 与素材处理 | AI 适配、图片与音频处理、后端交叉复核 | 外部服务和文件模块及相关验证 |
| E：内容与验收 | 样例、来源、物主反馈、独立试用与演示材料 | 完整内容包、验收记录与交付说明 |

人与 AI 的配合方式：

- 人负责产品取舍、素材使用范围、事实确认和最终验收。
- AI 在明确任务边界内实现、排查和验证，交付实际证据。
- C 组织公共契约，模块使用者共同核对输入输出，再按独立范围并行实现。
- 各成员使用独立工作目录和运行数据；公共文件变更与依赖合入按提交手册协调。
- 使用子代理遵守当前授权，不因任务较大自动扩大权限。

首轮联调优先确定公共展示数据，让工作台与场景消费同一份契约。接口未完成时使用同一 schema 校验过且明确标识的 fixture，真实保存和发布仍需接入服务端。

### 7.1 关键变更的复核职责

复核限于本次变更涉及的规则、差异和验证证据，不另设所有任务都必须经过的完整评审流程。

| 变更类型 | 复核负责人 | 重点 |
| --- | --- | --- |
| 权限与素材访问 | D 复核 C 的权限与路由；C 复核 D 的文件模块 | 服务端身份、资源归属、分享素材访问和撤销 |
| 发布与分享流程 | D 复核规则，A 验收流程，E 记录证据 | 人工确认、版本检查、快照隔离及参观链路 |
| 数据库迁移 | D 复核 C 的变更 | 数据兼容、约束、迁移结果及备份恢复 |

实现前落实复核人的姓名。复核范围若由本人实现，或复核人无法解释相关规则与结果，由 C 协调另一位具备相关能力且非作者的队员；涉及 C 自身或无法协调时由 A 指定。不得把参与实现者的检查记作独立复核。

仅一人可参与本次工作时，由实现者在实现结束后单独复查差异与验证证据，记录为“单人自查”。AI 可以辅助检查，但不能记作另一位人工复核者。复核记录注明实现者、复核者或单人自查、验证证据及未解决项。

复核未完成、相关验证失败或未执行，或存在未解决的权限、数据一致性及恢复阻塞问题时，该变更不得作为可合入、可部署版本交付；允许注明未验收状态后交接当前成果与缺口。按上述方式完成单人自查与相关验证，不因缺少第二位成员自动阻塞交付。

## 8. 开发依赖与推进方式

以 [团队执行方案第 7 节](TEAM_EXECUTION_PLAN.md#7-交付依赖与推进方式)的 G0—G5 为唯一交付包定义，不重复维护时间表。G0 建立公共工程和契约，G1 验证三维交互，G2 准备内容，G3 贯通人工制作与发布，G4 接入真实 AI 与完整展柜，G5 完成服务交付。

展柜原型、内容准备和独立 AI 验证可以并行；接入完整工程时满足对应契约与数据依赖。保存、确认和发布先通过人工展签贯通，不等待 AI。

比赛具体起止时间与材料要求由 A、E 核对正式通知；本轮不指定日期或工时。保存与发布尚未贯通时暂停额外装饰和新模型，优先完成主线。

删减顺序为：可选功能、额外主题、复杂动画、样例之外的新模型。不能用内存数据、假 AI 或只有图片的页面冒充已完成的核心产品。

### 8.1 演示建议

用一条故事串联演示：

1. 介绍一个具体的纪念需求。
2. 现场新增一件照片或票据类旧物并保存。
3. 真实调用 AI，修改一句展签，确认并发布。
4. 在另一浏览器打开链接，检视重点展品并播放原声。
5. 手机打开同一展馆。
6. 说明人工制作部分、服务成本、用户反馈和未完成项。

重点模型可以提前制作，现场新增内容采用实拍薄片。两者需要如实区分。

## 9. 技术与数据约定

本节是工程实施建议，不表示依赖、目录或命令已经建立。

### 9.1 建议技术方案

| 部分 | 建议 |
| --- | --- |
| 应用 | Next.js App Router、TypeScript strict |
| 界面 | React、Tailwind CSS |
| 三维 | Three.js、React Three Fiber、Drei |
| 公共契约 | Zod schema 及推导类型 |
| 数据 | PostgreSQL；服务端驱动由 C 在 G0 验证并锁定 |
| 素材 | 服务端持久目录，通过权限接口读取 |
| 身份 | 团队制作入口使用成熟会话或认证机制，具体选型由 C 落实 |
| AI | 一个服务端适配器，厂商由可用账号决定 |
| 验证 | 业务规则测试、接口测试和少量浏览器端到端测试 |

React 与 Fiber 的大版本需要匹配，并在初始化时固定依赖和锁文件，依据[官方兼容说明](https://r3f.docs.pmnd.rs/getting-started/installation)核对。类型检查与导入限制落实根目录 AGENTS.md 中已确定的配置要求。

数据库根据用户 2026年10月23日的要求确定为 PostgreSQL，其余技术选型仍按初始化验证结果落实。C 在 G0 固定 PostgreSQL 主版本和服务端驱动版本，提供必填连接配置 `DATABASE_URL` 与隔离测试库配置 `TEST_DATABASE_URL`，验证连接、迁移、事务与生产构建。连接串只保存在服务端配置，不进入客户端、Git 或日志；应用账号只授予业务所需权限。

首版部署保持单实例 Node 应用，连接独立的 PostgreSQL 服务，上传素材保存在服务端持久目录。PostgreSQL 的数据存储也必须持久化，不通过复制运行中的数据库目录共享开发环境。自托管入口配置参考[Next.js 官方说明](https://nextjs.org/docs/app/guides/self-hosting)。备份在暂停写入的同一窗口内生成 PostgreSQL 备份和素材目录副本，并验证配套恢复；数据库备份采用 `pg_dump` 自定义格式，恢复使用 `pg_restore`，参考 [PostgreSQL 备份与恢复文档](https://www.postgresql.org/docs/current/backup-dump.html)。当前尚无应用数据库，本轮只调整实施基线，不涉及既有数据迁移。

### 9.2 主要模块

- 页面与工作台负责输入和反馈。
- 故事模块负责展签、照片与音频展示。
- 场景模块负责柜体、模型、镜头与检视。
- 服务端负责身份、业务、数据库、素材和 AI。
- 公共契约负责请求、响应、展示数据和错误码。

浏览器不直接访问数据库、服务器文件路径或模型密钥。

### 9.3 最小数据实体

| 实体 | 作用 |
| --- | --- |
| 展馆 | 主题、版本、展品关系、当前发布状态 |
| 展品 | 名称、年代、格位、讲述、展签、展示方式和确认版本 |
| 素材 | 图片、音频的归属、格式、大小和服务端存储位置 |
| 整理草稿 | AI 输出、来源版本、追问和来源对应关系 |
| 发布快照 | 发布时冻结的公开内容与允许访问的素材集合 |

以上是职责层面的实体草案。C 按方案 A 落实团队身份和展馆、展品、素材之间的关联，不提前增加自助模式结构。

发布快照指发布时冻结的一份内容。修改工作台草稿不会立即改变参观页面，再次发布后才更新。

必须保持的规则：

- 公开内容变化后，展品版本增加，旧确认失效。
- 保存与发布携带预期版本，冲突明确返回。
- 发布在事务中检查版本、确认状态、素材归属与格位；未确认内容阻止发布并列明需要处理的展品。
- 同馆有效展品不能占用同一格位。
- 替换素材产生新文件，不覆盖旧快照引用的内容。
- 草稿删除不破坏已有发布版本；首版不自动物理清理历史素材。
- AI 调用在数据库事务外执行，过期结果不能覆盖新编辑。
- 文件写入与数据库提交分别处理失败；只有完整可读的素材才被有效引用，不能因响应发送失败而误删已提交素材。

### 9.4 接口职责

| 接口组 | 职责 |
| --- | --- |
| 身份与会话 | 进入和退出制作入口 |
| 展馆 | 创建、读取和修改馆资料 |
| 展品 | 创建、保存、读取和移除旧物 |
| 素材 | 上传、校验、保存及授权读取 |
| AI 整理 | 基于已保存的指定版本生成草稿 |
| 确认 | 明确确认当前版本 |
| 发布 | 检查全馆状态并生成快照 |
| 分享 | 读取当前快照、停止分享、更换链接 |
| 健康检查 | 返回应用和关键依赖是否可用 |

公共请求、响应与错误结构统一维护。身份与资源关联接口按方案 A 细化，首版不实现客户自助注册及个人工作台接口。

公开展示与分享接口只返回公开展示数据，不包含原始讲述和 AI 内部草稿；受保护的工作台接口按权限返回编辑所需字段。所有接口均不得泄露存储路径或凭据。

素材接口使用第 9.7 节的限额，所有业务接口采用第 9.8 节的错误契约。成功响应统一为 `{ data: ... }`。

### 9.5 分享与素材

参观链接采用服务端生成的高熵随机 token，属于“持有链接即可访问”。

页面、数据和私有素材请求均检查当前分享状态。素材还需属于当前发布快照，原始上传不进入公开静态目录。

对外展示、缩略图和贴图使用正确处理方向、清除定位及设备敏感元数据的图片版本。若保留原始文件，只允许相应授权访问，分享接口不能绕过处理直接返回原图。

停止分享或更换链接后，旧 token 不能发起新的有效访问。私有及可撤销分享内容禁止存储缓存，需检查应用框架与代理配置；素材响应使用经过验证的 Content-Type 和 X-Content-Type-Options: nosniff。已经下载的副本不承诺撤回。

### 9.6 受信任模型清单与空间约定

| 项目 | 固定约定 |
| --- | --- |
| 格式 | GLB，贴图内嵌 |
| 坐标与单位 | 右手坐标系，Y 向上，正面朝 +Z，长度单位为米 |
| 原点 | 交付模型的底部中心位于原点 |
| 入柜适配 | 使用包含节点变换的完整包围盒，按柜格宽、高、深计算最小等比缩放，三轴均预留 10% |
| 恢复目标 | 根据稳定柜格布局与模型初始变换计算，独立于动画中间状态 |
| 不合规资产 | 入清单前修正资产，不在渲染代码中增加逐件临时补丁 |
| 清单字段 | modelKey、路径、版本、来源、许可、近似程度、缩略图 |

柜格尺寸指可用于摆放的内部宽、高、深。缩放系数为 `0.9 × min(格宽/模型宽, 格高/模型高, 格深/模型深)`，适配后各轴占用不超过该轴可用尺寸的 90%。

窗口尺寸或布局变化后，按新布局重新确定恢复目标，不从动画中间位置采样覆盖基准。

坐标和单位依据 [glTF 规范](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units)；原点、边距属于本项目约定。

### 9.7 上传格式与限额

| 项目 | 首版取值 |
| --- | --- |
| 图片格式 | 静态 JPEG、PNG、WebP |
| 图片文件上限 | 10 MiB，即 10,485,760 字节 |
| 图片尺寸 | 宽、高各不超过 8192 像素，且总像素不超过 32,000,000 |
| 音频格式 | MP3、M4A（AAC）、WAV（PCM） |
| 音频文件上限 | 20 MiB，即 20,971,520 字节 |
| 用户上传模型 | 不开放，使用受信任模型清单 |

字节与像素限额均检查原始输入，不能先完整解码超限图片再缩小。像素值作为首版资源预算，后续通过实际素材和部署环境验证；图片处理库支持设置输入像素限制，参考 [Sharp 文档](https://sharp.pixelplumbing.com/api-constructor/)。

允许格式、文件签名与实际解析结果需要一致，不能只凭扩展名或客户端 Content-Type 接受上传。音频还需在实际验收浏览器上验证播放。格式不在允许范围时返回 415；允许格式的文件损坏或图片尺寸超限时返回 400；文件字节数超限时返回 413，具体错误码见下一节。

### 9.8 错误契约

失败响应的基础结构为 `{ error: { code, message, requestId } }`。message 提供可理解的操作提示，requestId 用于关联诊断；错误响应不泄露凭据、内部路径或私密内容。

`NOT_CONFIRMED` 返回 HTTP 409，并必须包含 `error.details.unconfirmedExhibitIds`。其余错误维持基础结构。示例：

```json
{
  "error": {
    "code": "NOT_CONFIRMED",
    "message": "请先确认列出的展品后再发布。",
    "requestId": "request-example",
    "details": {
      "unconfirmedExhibitIds": ["exhibit-example"]
    }
  }
}
```

`unconfirmedExhibitIds` 是非空、无重复的展品 ID 数组，只列出当前已授权展馆中未删除且当前版本尚未确认的展品。前端通过该字段定位需要处理的展品，不从 message 解析清单；身份、归属和版本校验仍按既有规则执行。

| HTTP | 错误码 | 含义 |
| --- | --- | --- |
| 400 | VALIDATION_ERROR | 字段、尺寸或文件内容校验失败 |
| 401 | UNAUTHORIZED | 未登录或会话失效 |
| 403 | FORBIDDEN | 已识别身份不允许执行该操作 |
| 404 | NOT_FOUND | 受保护资源不存在或对当前身份不可见 |
| 404 | SHARE_NOT_FOUND | 分享不可用，或素材不属于当前分享快照 |
| 409 | VERSION_CONFLICT | 预期版本与当前版本不符 |
| 409 | NOT_CONFIRMED | 发布内容尚未完成当前版本确认 |
| 413 | PAYLOAD_TOO_LARGE | 上传文件字节数超限 |
| 415 | UNSUPPORTED_MEDIA_TYPE | 文件格式或编码不在允许范围 |
| 502 | AI_UNAVAILABLE | 模型服务失败或输出不可用 |
| 504 | AI_TIMEOUT | 模型调用超时 |
| 500 | INTERNAL_ERROR | 未预期的服务端错误 |

需要隐藏资源存在性的受保护入口使用 NOT_FOUND；FORBIDDEN 不用于暴露当前身份不可见的私有资源。分享入口不区分 token 失效、素材不存在与素材无权访问，统一返回 404、SHARE_NOT_FOUND 和相同的对外提示。

版本冲突返回 409、VERSION_CONFLICT，前端保留未保存输入，提示刷新或核对差异，不自动覆盖或盲目重试。

## 10. 怎样判断完成

### 10.1 验证触发与范围

| 触发条件 | 执行范围 |
| --- | --- |
| 修改局部逻辑、页面或样式 | 验证受影响的不变量与关联流程，选择相关场景和设备 |
| 工程初始化 | 建立类型检查、lint、业务测试和生产构建的实际入口，并落实相应 CI 检查 |
| 首次完整上线或影响多个核心流程的变更 | 执行适用制作模式下的完整核心流程验收，覆盖第 10.2 节全部适用场景及桌面、手机操作 |
| 实际部署 | 核对生产构建、静态模型、原生依赖，并验证重启后数据和素材仍可读取 |

局部修改不默认执行整表。未选择的制作模式及未纳入首版的可选功能不进入本次验收；关键变更还需满足第 7.1 节的复核条件。

### 10.2 验收场景

下表是未来实现的验收要求，尚无运行结果。格式、字节和像素边界用例均以其他校验条件满足为前提。

| 验收场景 | 预期结果 |
| --- | --- |
| 保存后刷新、重启服务 | 展馆、展品、素材和发布状态仍然存在 |
| 未登录访问草稿和原始素材 | 返回 401、UNAUTHORIZED |
| 团队请求将不属于目标展馆的素材用于保存或发布 | 请求被拒绝；需要隐藏资源存在性时返回 404、NOT_FOUND，不能产生跨馆错误引用 |
| 确认后修改内容 | 旧确认失效，未经再次确认不能发布；返回 409、NOT_CONFIRMED，error.details.unconfirmedExhibitIds 完整列出本馆有效的未确认展品 |
| 修改草稿但不发布 | 参观者仍看到上一份快照 |
| 分享仍启用时，删除草稿展品或替换图片、音频，但不重新发布 | 参观页仍显示旧快照，旧图片和音频仍可读取；替换不覆盖或误删旧文件 |
| 使用旧版本保存或发布 | 返回 409、VERSION_CONFLICT，保留未保存输入，不覆盖新内容 |
| 停止分享或更换链接 | 旧数据与私有素材的新请求均返回 404、SHARE_NOT_FOUND |
| 有效分享 token 请求不属于当前快照的素材 | 返回 404、SHARE_NOT_FOUND，对外提示与无效分享一致 |
| 上传允许的静态 JPEG、PNG、WebP | 通过内容与尺寸等校验后可保存，正常显示 |
| 上传允许的 MP3、M4A（AAC）、WAV（PCM） | 通过内容与大小校验后可保存，在验收浏览器播放和停止 |
| 上传格式不在允许范围，包括动态图片或非允许的音频编码 | 返回 415、UNSUPPORTED_MEDIA_TYPE |
| 伪造扩展名或 Content-Type，或上传无法解析的允许格式文件 | 根据实际格式或解析结果拒绝；不允许格式返回 415，文件损坏返回 400 |
| 图片恰好 10,485,760 字节、音频恰好 20,971,520 字节 | 其他校验均通过时允许上传 |
| 图片或音频超过各自字节上限 1 字节 | 返回 413、PAYLOAD_TOO_LARGE |
| 图片某轴为 8192 像素且总像素未超限 | 其他校验均通过时允许；任一轴为 8193 像素则返回 400、VALIDATION_ERROR |
| 图片为 6400 × 5000 像素，即 32,000,000 像素 | 其他校验均通过时允许；6400 × 5001 则返回 400、VALIDATION_ERROR |
| 上传中断或数据库事务失败 | 有效记录不引用不完整文件，已有素材不被误删，未提交残留可定位 |
| 数据库提交成功后响应发送失败 | 不误删已提交素材，先核对写入结果，不盲目重放非幂等操作 |
| 分享带有测试用定位信息的照片及缩略图 | 对外处理版本不含该定位元数据，方向正确，不能绕过接口取得原图 |
| AI 超时或输出无效 | 返回 AI_TIMEOUT 或 AI_UNAVAILABLE 对应状态，原文保留，允许人工继续 |
| AI 请求期间修改讲述或展签，旧请求随后返回 | 最新讲述、展签与确认状态不被旧结果覆盖；采纳时核对来源版本，不匹配则拒绝采纳 |
| 快速选择、旋转、返回 | 无重复模型、镜头卡死或旧音频持续播放 |
| 取出途中按 Esc、连续切换并调整窗口 | 展品和镜头恢复到当前布局的正确位置，不使用动画中间状态作为恢复基准 |
| 按清单加载不同尺寸的模型 | 朝向、落点和格位适配一致，包围盒符合第 9.6 节约定 |
| 模型失败或 WebGL 不可用 | 有明确状态和可用的故事入口 |
| 模拟运行期间 WebGL 上下文丢失 | 故事仍可访问，有明确恢复入口，不无限重建 Canvas |

### 11.1 收费方向：前期定制，后续会员

根据 2026年10月23日补充的想法，保留两个阶段的收费设想：

| 阶段 | 服务形态 | 需要验证的问题 |
| --- | --- | --- |
| 前期：定制服务 | 为个人、家庭或共同记忆制作私密纪念展，按定制服务收费 | 客户愿意为什么付费，制作成本与可接受价格是否匹配 |

定价、套餐、会员权益、阶段切换条件和支付方式尚未确定。付费或成为会员不等于同意公开作品；公开展示需要单独选择。这些是商业假设，首版仍不接入支付系统。

## 12. 后续功能想法

记录日期：2026年10月23日。来源为本次提供的功能讨论截图，状态为已收录、待范围取舍与排期。本节补充产品方向，保留 v0.6 的方案 A 实施基线；下面描述的页面、账号能力和交互尚未实现，也不作为本轮 G0—G5 的交付要求。

### 12.1 公开展示平台与私密定制交付

建设一个公开可见的网站，展示愿意公开自己纪念物和生平事迹的人的展馆。路人可以参观展品、阅读不同人的经历；网站同时作为作品展示平台和吸引定制客户的主要入口。

- 首页开局可以展示一个固定展馆，也可以每日随机展示一个展馆；两种方式作为候选，后续择定。被展示的作品必须已获准公开。
- 希望私密定制的客户，制作完成后可以在网站内的个人私人展馆查看，也可以选择只包含自己展品的独立网站。
- 公开展馆可以进入发现、搜索、地图和排行榜；私人展馆不进入这些公开入口。
- 私人展馆及独立网站的访问方式需另行确定，例如持链接访问或指定账号访问。独立网站只是交付形态，本身不代表私密；现有分享链接仍准确描述为“持有链接即可访问”。

站内私人展馆所需的客户账号、独立网站的托管维护与交付成本，均需在采用该方向时明确；不能把目前的团队内部工作台直接当作客户个人空间。

### 12.2 “世界”入口、好友互动与展馆发现

在主界面左上角设置“世界”入口，打开后按“附近的人 → 好友 → 排行榜”的顺序组织发现入口，并提供搜索。用户可以进入他人的公开个人博物馆，在留言区留言或收藏（star）。

进一步提供全球视角：用户选择想看的地域，参观当地个人或多人共同展馆。好友关系的建立方式、“附近”的地域范围、搜索字段及留言管理方式仍需确定。

地图与榜单的设想：

| 能力 | 想法 |
| --- | --- |
| 全球地图 | 按地域发现展馆；时间不足时可先覆盖中国 |
| 热门展馆亮点 | 个人或共同展馆超过 1 万人浏览后，在地图对应地区点亮；亮度随浏览量档位变化 |
| 总浏览量榜 | 按展馆累计浏览量排行 |
| 收藏榜 | 按展馆收藏（star）数量排行 |
| 近期浏览量榜 | 提供年、月、日的浏览量排行 |
| 国家维度榜单 | 按国家筛选展馆的浏览量榜和收藏榜；首期也可只做中国范围 |

“超过 1 万人浏览”作为当前讨论中的亮点门槛记录，浏览人数与浏览次数需区分。亮度分档、有效浏览与访客的去重口径、年/月/日采用自然周期还是滚动窗口，以及国家维度是否还需要国家间汇总排名，均待确定。

平台可发现的“公开”需要明确授权，不能将已有参观链接自动收录进首页、搜索、地图或榜单。附近和地图位置采用用户同意展示的地域信息，不默认展示精确住址或实时位置。作品退出公开展示后，应退出相应发现入口。

### 12.3 AI 访谈与个人自传

在未来的个人工作台中增加“个人自传编写”选项。用户进入后与 AI 对话，AI 通过逐步提问帮助回顾经历，再把用户提供的内容整理成自传草稿。

- 可调研并引入 GitHub 上的自传编写 skill，借鉴其访谈与整理流程；具体仓库尚未提供，采用前核对内容、许可及适配方式，不直接执行未经检查的外部脚本。
- 用户可以补充、修订并确认自传，AI 保留记不清或不确定的内容，不补造人生经历。
- 确认后的自传以书籍形式放在博物馆中央，封面显示用户名，参观者可打开阅读获准展示的内容。
- 对话记录、自传草稿和确认后的展示版本分别保存；自传公开范围由用户决定，不随展馆公开而自动公开全部访谈内容。

这项能力依赖个人工作台、长篇内容保存与书籍阅读交互，需另行明确篇幅、章节形式和确认方式，不直接套用首版短展签的字数限制。

### 12.4 邀请共同作者

制作展品或故事作品时，可以邀请相关作者，用于呈现两人或多人之间的关系和回忆。被邀请人可以接受或拒绝；接受后才作为共同作者展示，待回应或已拒绝不能被当作共同署名已获同意。

共同作者可以是共同经历的讲述者或内容贡献者。共同署名、编辑权限和发布确认是不同的事项：是否允许共同编辑、哪些修改需要谁确认，以及退出合作后的署名和内容如何处理，均在实现前明确，不能由邀请接受操作自动推定。

### 12.5 不依附实物的故事展品

展品不必局限于具体旧物，也可以是一段经历、一段人与人之间的故事，或一个时代的记忆。没有对应实物也能作为独立内容被收藏和参观，不要求用户为了建展品而虚构物品或提供无关照片。

可探索以故事卡、信件或书页作为柜内入口，选中后展示文字、照片与原声；这些是呈现候选，尚未确定最终形式。时代背景与个人回忆需要区分来源，AI 仍只整理有依据的内容。

采用该方向时需调整当前以旧物名称、实拍和模型为中心的收录与展示契约，明确故事类展品的必填内容及无实物时的参观方式。

### 12.6 多人共同记忆

展馆和展品可以承载多人的共同记忆，既可以围绕共同纪念物，也可以围绕一段共同经历：

- 情侣或夫妻的爱情故事与纪念物。
- 创业团队的共同经历与阶段纪念。
- 社区、社会组织等群体的共同记忆与纪念物。

同一作品可以保留不同参与者的讲述，并标明各自来源；记忆不一致时不由 AI 合并成一个确定事实。涉及共同署名时衔接第 12.4 节的邀请机制，公开内容及人物信息按相应授权范围展示。

共同记忆是内容方向，不等于必须先建设实时协作或多级组织权限。关系展示、多人确认和后续维护由谁负责，需要在该功能进入实施范围时确定。
