# 黑客松通用打法（选题无关）

> 这份是从上一版作战板里剥出来的**通用部分**——时间账、并行机制、最后 6 小时清单、团队配置。
> 换选题不用改这里；只有「做什么产品」的部分需要重写。
>
> 来源：Qoder-cn《黑客松高效工作与分工·国内外调研》（2026-10-20）+ 上一版排期踩过的坑。

---

## 1. 时间账：先算清楚，再排期

名义时长不等于产能。扣掉睡眠、吃饭、联调、答辩准备，再乘 0.7 效率折损：

| 段 | 可用人时（按 2 个编码者） | 特点 |
|---|---|---|
| 赛前 | 2 人 × 16h ≈ **32 人时** | 分散、易被打断、但无压力 |
| 比赛（24日 08:30 – 25日 16:00） | 2 人 × 30h ≈ **60 人时** | 集中、但疲劳、要留答辩 |

- **两段合计有效人时 ≈ 55–60 人时**
- **只靠比赛期，有效人时 ≈ 28 人时**

> **外部读数**：48 小时名义时长扣除睡眠后，**深度工作只有 8–14 小时/人**。
> 按这个口径，32 小时里 2 个编码者的深度工作时长约 **10–18 人时**。
> ⇒ 28 是"有效人时"（含联调、对齐、修小问题），**不是"能写新代码的时间"**。排期按更紧的那个算。

**两条推论**：

1. **「提前做」不是可选项，是唯一解。** 它把可用产能翻了一倍。
2. **时间紧的解法是「缩范围 + 前移」，不是「加人」。** 缩范围不依赖外部条件，今天就能生效；加人要赌一个人靠谱。

## 2. 范围：只保留一条最小可演示闭环

**格式固定为一条链路**，用一句话能说完，且能在 3 分钟内演示：

```
输入 → 处理 → 输出 → 数据留下
```

**建议砍掉的三类**：

| 类型 | 为什么砍 | 什么时候别砍 |
|---|---|---|
| 多租户 / 多组织架构 | demo 只需要一份数据；工程实现不等于产品故事 | 评分明确要求"支持多机构入驻" |
| 独立的说明页 / 关于页 / 隐私页 | 降级为主页面底部一段说明 + 锚点 | 评分里"合规/隐私"占比高 |
| 第三种及以上的页面 | 两页就能走完闭环 | — |

> **注意措辞**：砍的是**工程架构**，不是**产品故事**。故事必须完整，实现可以简陋。

## 3. 并行：真正的来源是契约先行，不是角色分工

按层分工（前端 / 后端）有 **3 个等待点**：等接口、等页面、等决策。
最贵的浪费不是"谁没在干活"，是"互相等"。

**解法：先定契约，再开工。** 契约就是接口形状，30 分钟能写完：

```
POST /api/<动作>
  body: { ...字段... }
  resp: { id: "..." }

GET  /api/<查询>?id=...
  resp: { items: [ { id, score, reasons: ["...", "..."] } ] }
```

契约定完之后：

- **A 用 mock 数据先把页面做出来**，不等 B 的接口
- **B 按契约先把接口做出来**，不等 A 的页面
- 联调时一次接通，而不是边做边对齐

**契约定完再补两行，就凑成一页规格（抑制赛中需求漂移）：**

- **验收标准**：怎么算做完？多久出结果？在什么设备上能跑？
- **高危操作黑名单**：不写死任何 key；不改数据结构而不通知；演示前 3 小时不动部署

### 两种分工法

| 方案 | 做法 | 什么时候用 | 代价 |
|---|---|---|---|
| **按层** | A 全前端，B 全后端 | 一人只会前端、一人只会后端 | 3 个等待点，必须契约先行 |
| **按页面**（垂直切片） | A 做页面 1 全栈，B 做页面 2 全栈 | 两人都能写全栈（哪怕粗糙） | 都碰数据层、风格不一 |

**判据**：两人都能写全栈 → 按页面；有一人只会前端 → 按层 + 契约先行。**等队友回了技能栈再定，别提前锁死。**

### 每 3 小时问一句"你在等谁"

等待是最贵的浪费，而且**没人会主动说**。站会三句里第 ③ 句（卡在哪）要具体到"我在等谁的什么"，
不能答"还行"。发现两人互等 → 立刻改成契约先行或换分工。

## 4. 最后 6 小时：固定动作，不做新东西

| 时段 | 事 | 人 |
|---|---|---|
| −6h ~ −3.5h | 修昨夜遗留 + 界面收尾 | 开发 |
| −3.5h ~ −2.5h | **极端场景测试**：断网 / 重复提交 / 空输入 / 超长输入 | 开发 |
| −2.5h ~ −1.5h | 材料定稿（12 页以内、去目录页、少动画）+ 讲稿 + demo 脚本（谁说什么、点哪里） | 主讲 |
| −1.5h ~ −0.5h | **彩排 3 遍**，掐表，第三遍录屏 | 全员 |
| −0.5h ~ 0h | **应急预案** + **材料清点** | 主讲 |
| **提前 1 小时** | **提交** | 主讲 |

**应急三件套**（每条都要事先准备好，不是当场想）：

| 故障 | 预案 |
|---|---|
| 服务器崩 / 网络断 | 本地跑起来，或切录屏 |
| 演示材料打不开 | 手机里存一份 PDF |
| 视频放不出 | 本地 mp4，不依赖在线播放 |

> **现场翻车不解释技术细节、不当场 debug**，立刻切备用方案。演练时就规定好谁喊"切"。
> 调研里这条是高频踩坑：评委看的是"能不能演示"，不是"你能不能修"。

> **材料的 deadline 不是截止时间，是截止前 2 小时。** 截止之后通常还有答辩，材料是答辩的道具，不是提交物。

## 5. 团队配置

**共识配置：3–4 人 = 2 开发 + 1 产品 + 1 Pitchman**。

> 原文强调：「Pitchman 被反复强调——开发到路演时神志不清，专职宣讲人能撑住评委问答。」
> 另一条：**约 5 人团队获奖率显著高于 8 人以上大团队**，沟通成本随人数暴涨。

⇒ **上限是 4 人**，第 5 个人带来的协调成本会吃掉产出。

**加人前先算成本**：

| 成本 | 量级 |
|---|---|
| 招人 | 2–5h（找人 + 说服 + 对齐，成功率不确定） |
| Onboarding | 2–4h（读文档 + 跑通环境 + 首次提交被门禁拦） |
| 协调 | 沟通链路 3 条 → 6 条 |

**不要为了加产能而加第二个程序员**——代码不是"人多就快"的活，两个人改同一个仓库，冲突成本可能吃掉新增产能。

## 6. 红线

| # | 红线 | 违反了会怎样 |
|---|---|---|
| 1 | 不加功能 | 时间更不够，最后交个半成品 |
| 2 | 不通宵 | 最后半天全员脑死亡，质量归零 |
| 3 | 不用假数据冒充真实成果 | 评委一问来源就穿帮 |
| 4 | 不拖到最后一小时提交 | 网络一抖就白干 |
| 5 | 不让队友"自己看着办" | 最后发现两人做了同一个东西 |

---

## 7. 站会（10 分钟）

每人三句，不许展开：① 昨天那件事做完没 ② 今天做什么 ③ 卡在哪。

> 站会不是汇报，是**暴露阻塞**。
