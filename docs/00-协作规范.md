# 协作规范（小队版·别加流程）

> 几十小时的项目，流程越轻越好。这份只规定**会真的出事的五件事**：分支、冲突、同步、目录、日志。
> **提交信息格式、PR 内容要求、AI Agent 条款、自动拦截规则，全部在 `01-提交与PR规范.md`**——以那份为准，这里不重复。

---

## 1. 分支

| 分支 | 谁推 | 规则 |
|---|---|---|
| `main` | 只能通过 PR 合 | 始终可运行。合进去的东西必须能跑 |
| `feat/<角色>-<做什么>` | 各自推 | 例：`feat/a-login-page`、`feat/b-data-api` |

- **不要直接 push 到 main**（除非是改 README 这种零风险改动）。
- 一个分支活不过 24 小时。开太久必然冲突。

---

## 2. 提交

格式、类型、拆分标准、禁止项 → 见 `01-提交与PR规范.md`。

**这里只重复一条最容易忘的**：一次提交只做一件事。别把「改样式」和「改接口」放进同一个 commit——出问题回滚不了。

> 钩子会自动拦格式错误、空壳文件、调试残留、巨型提交。装一次：`bash scripts/install-hooks.sh`

---

## 3. PR

三行必填：改了什么 / 怎么验证的 / 影响谁。模板已配好。

- **谁写谁合**，不用等评审。
- 合之前先 `git pull --rebase origin main` 跑一遍。
- 合完立刻在群里说一句"已合，可以拉了"。

> **PR 描述必须由人写，不能 AI 代写。** 理由见 `01` 第五节——这段文字是唯一能证明你读过自己代码的东西。

> 几个人不需要 code review 流程。需要的是**别人拉下来不会崩**。

---

## 4. 冲突

| 情况 | 做法 |
|---|---|
| 同一个文件两人都在改 | **停下来，群里说一句**，一个人改完另一个再动 |
| 已经冲突了 | 后合的人 rebase，**不要用 `--force` 推 main** |
| 不确定谁对 | 保留能跑的那版，另一版先存成 `.bak` 再说 |

---

## 5. 每日同步

**21:00 站会，10 分钟**：每人三句，不许展开——① 昨天那件事做完没 ② 今天做什么 ③ 卡在哪。

> 第 ③ 句必须具体到「我在等谁的什么」，不能答「还行」。等待是最贵的浪费，而且没人会主动说。

**22:30 收尾，一行日志**，追加到本文档 §7。

---

## 6. 目录约定（避免两人抢同一个文件）

> 选题定下后填具体路径。下面是骨架，**先定好谁的地盘，再开工**。

```
app/ 或 src/     界面与页面
lib/             业务逻辑、数据访问（不放界面代码）
data/            数据集、内容定义
docs/            文档
scripts/         工具与门禁
```

**跨地盘改文件前先在群里说一句。** 这是小队项目里 80% 冲突的来源。
