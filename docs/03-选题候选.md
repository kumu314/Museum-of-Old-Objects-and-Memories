## 0. 结论先行

1. **归档引擎没有任何一行代码能搬进这 6 个赛道。** 它是「室友匹配」的领域逻辑：5 个导出函数全部以 `person / answers / survey` 为入参，换选题后类型全错。
2. **能搬的是三个「形状」和一个「评估思路」**：规则写在数据里而不是代码里、每条结论带依据、纯函数可单测；以及「把约束放回真实场景检验」。其中**用餐**拿到的收益最大，**查证**次之，其余四个为 0。
3. ⇒ 选题不该由「引擎能不能复用」来定。判据换成两条：**两条验收线能不能 100% 机械证明** + **赛前能提前做完多少**。按这把尺子，推荐顺序 **用餐 > 游戏 > 办公**。
4. **新读数（10-21 17:30 补）**：同系列赛事无锡站通稿写明评审含「**选手人气投票**」、交付是「**项目提交 + 演示 demo**」。这抬高了"3 秒看懂"的权重，也意味着赛道拥挤度是真实成本——两条都对我们不利 C（办公，最挤、要解释才懂）。详见 §6。

## 1. 六条赛道与两条验收线（海报原文固化）

> 这一节是为了下次不用再翻截图。海报上每个赛道恰好两个色块，就是两条验收线。

| # | 赛道 | 题目 | 一句话要求 | 验收线 A | 验收线 B |
|---|---|---|---|---|---|
| 1 | 效率工具 | **办公**·让 AI 真的 Work | 做一个同事每天都想用的 AI 工具，拿来就用，用完交差 | **真实任务**：会前简报 / 会议待办 / 汇总周报，**选一件做好** | **交付能用**：输入需求 → 完成任务 → 结果拿来就能用 |
| 2 | 创意开发 | **用餐** | 做一个能**实际运行**的用餐 Skill，把饭点安排明白 | **用餐需求**：人数、预算、口味与饮食偏好 | **用餐方案**：搭配清晰、**总价与选择有依据** |
| 3 | 短剧创作 | **短剧**·三集追更 | 用 AI 讲一个故事，让人看完还想看下一集 | **3 集竖屏**：一个故事，连续三集 | **每集 30–60 秒**：让下一集成为期待 |
| 4 | 查证 | **查证**·AI 侦探社 | 做一个查证工具，把结论的来路查清楚 | **作品方向**：开发一个查证工具，输出**带来源的查证卡** | **让判断有据可查**：结论有依据、来源可追溯 |
| 5 | 游戏创作 | **游戏**·让人想再玩一局 | 做一个小游戏，闯关 / 解谜 / 派对，玩法由你定 | **一看就会玩**：浏览器或手机直接玩 | **完整玩一局**：开始、挑战、结算，玩完还能再来一局 |
| 6 | 产品创作 | **OPC**·一个人就是一家公司 | 一个人加 AI，把想法做成**能对外服务**的产品 | **找准客户**：客户需求是什么 | **跑通交付**：能用的产品 + 样例交付，讲清怎么收费 |

**共同结构**：每个赛道都是「一个具体任务 + 一条可验收的交付标准」。这不是创意赛，是**交付赛**——两条线都命中才算完成，任一条缺失直接掉档。

### 逐赛道结论

| 赛道 | 复用度 | 具体能用的东西 |
|---|---|---|
| **用餐** | ★★★ | 硬约束（忌口 / 预算上限）= `hardRules`；「选择有依据」= `breakdown` 逐项理由；`room-eval` 的穷举换成「预算内可行组合空间有多大」——**这是验收线 B 的直接证据** |
| **查证** | ★★ | `evidence` 对象形状（结论 + 依据 + 来源）+ 可证伪的测试纪律。但检索与溯源层为 **0**，那才是这条赛道的主体工作量 |
| 办公 | ★ | 只剩「规则写 JSON」「纯函数可单测」。代码 0 行 |
| 游戏 | ✗ | 无。游戏不需要加权打分 |
| 短剧 | ✗ | 无 |
| OPC | ✗ | 只有当产品形态恰好是「推荐 / 匹配」时才沾边 |

**一句话**：引擎的价值不在代码，在**它被逼出来的三个习惯**——规则外置、结论带依据、场景级覆盖率。这三个习惯恰好是「用餐」和「查证」两条验收线的原文要求。

## 3. 三个候选

> 口径：人时按 `02-黑客松通用打法` 的算法——赛前 32 人时（分散、无压力）+ 赛中 60 人时（2 个编码者）。
> 「赛前可完成」指赛前就能做完、赛中只做打磨与联调的比例。

### 候选 A · 用餐 Skill（创意开发赛道）— 推荐

- **是什么**：输入人数 / 预算 / 口味与忌口，输出一份**可直接下单**的搭配清单：每道菜 + 单价 + 一句话入选理由 + 合计；预算有余时给「再加 ¥12 可以多一个荤菜」的可选升级。核心是一个带硬约束的组合求解器，不是聊天壳。
- **给谁**：宿舍 / 社团聚餐里被群里 @ 问「吃啥」的那个人。
- **凭什么好**：
  - 验收线 A 的三个输入字段是**有限枚举**，可以穷举验证；验收线 B 的「总价与选择有依据」正好是引擎 `breakdown` 的形状。
  - 我们能给**读数**而不是口头保证：「200 组随机输入，预算与忌口违反 0 例，平均求解 40ms」——这句话直接就是验收线 B 的证据。
  - demo 极快：6 人 / ¥150 / 2 人不吃辣 → 3 秒出 ¥148 的清单。3 分钟讲得完。
- **多久能做完**：求解器 4–6h + Skill 对话壳 3–4h + 界面 2–3h + 验证脚本 2h ≈ **12–15 人时**，赛前可完成 **65–70%**。
- **代价 / 风险**：
  - **容易做小**。评委可能一句「不就是个点菜器」否掉。必须靠三件事拉开：真实菜单数据、忌口当硬约束（不是软偏好）、每一分钱都有出处。
  - **形态有前提**：海报写的是「Skill」。如果主办方指的是某个 agent 平台的 skill 格式，交付形态就被锁死，须先确认（见 §6）。

### 候选 B · 游戏（游戏创作赛道）— 确定性最高

- **是什么**：单文件 HTML 小游戏，一个核心机制做透（重力翻转跑酷 / 合并塔防二选一），3 秒看懂，一局 60–90 秒，结算页给分数 + 「再来一局」。
- **给谁**：群里随手点开链接的同学，不需要装任何东西。
- **凭什么好**：
  - 两条验收线**全是机械可验证的**：浏览器直接打开就能玩 / 开始-挑战-结算-重开四个动作都能点。不依赖任何外部服务 ⇒ **demo 零翻车风险**，直接对冲「现场翻车」这条红线。
  - 本机已有本地 HTML 复核能力（无头浏览器拍渲染 + 交互断言 + 几何检查），能把「能玩」变成读数而不是感觉。
- **多久能做完**：核心玩法 6–8h + 难度曲线 3h + 手感打磨 4h + 结算与音效 2h ≈ **15–17 人时**，赛前可完成 **60–70%**。
- **代价 / 风险**：
  - **「让人想再玩一局」是主观的**。我们能证明「能重开」，不能证明「想重开」——验收线 B 的前半句（开始/挑战/结算）硬，后半句（还想再来）软。
  - 同赛道拼手感，方差大；我们三个都不是做游戏的，审美天花板可能不够。

### 候选 C · 办公 · 会议待办（效率工具赛道）— 门槛最低，但最挤

- **是什么**：一段会议录音 / 纪要 → 「谁 · 在什么时候前 · 做什么」的可勾选待办清单，一键导出到日历或清单工具。
- **给谁**：一周开三次会、但没人写纪要的学生团队 / 小团队。
- **凭什么好**：
  - 验收线 A **明确给了三选一**（会前简报 / 会议待办 / 汇总周报），范围天然受限，不用自己找边界。
  - 「结果拿来就能用」可以用真实会议录音当场验证，证据链短。
- **多久能做完**：语音转写接入 2h（或直接吃文本）+ 抽取结构化 4h + 去重合并 3h + 导出 2h ≈ **11–13 人时**，赛前可完成 **50%**。
- **代价 / 风险**：
  - **这条赛道最挤**。几乎所有人的第一反应都是它，同质化最严重；差异化只能靠「结果真的能用」（精确到人 + 时间 + 可勾选），否则就是又一个 AI 总结器。
  - **依赖外部 API**：key、额度、现场网络任一环节抖动都会翻车，是三条里唯一有「不可控外部依赖」的。

## 4. 同一把尺子对比

| 维度 | A 用餐 | B 游戏 | C 办公 |
|---|---|---|---|
| 验收线 A 可机械证明 | 强（输入字段有限，可穷举） | 强（能打开就能玩） | 中（要真人会议录音） |
| 验收线 B 可机械证明 | **强**（总价 + 每项理由，可脚本断言） | 中（前半硬、后半软） | 中（可用性靠人判断） |
| 赛前可提前完成 | **65–70%** | 60–70% | 50% |
| 3 分钟 demo 清楚度 | 强（一句话就懂） | 强（不用解释） | 中（要讲清"比总结器强在哪"） |
| 外部依赖 / 翻车点 | 低（可全本地） | **最低（零依赖）** | **高（API key / 额度 / 网络）** |
| 同质化风险 | 中 | 中 | **高** |
| 需要的稀缺能力 | 约束求解 + 数据整理 | 手感 + 审美 | prompt 工程 |
| 人时估算 | 12–15 | 15–17 | 11–13 |

**分母说明**：6 个赛道我们只能报 1 个。上表只比了 3 个候选，另外 3 个的排除理由见 §5——不是因为它们更差，是因为**和我们这支队伍的能力错配**。

| 赛道 | 排除理由 | 如果非要选的代价 |

## 6. 外部读数：同系列赛事的公开规则 ⚠ 本节对本次比赛不适用（10-21 18:30 标注）

> **作废原因**：本校比赛是**校内赛**，只套用了那套选题标准，不是 WaytoAGI 官方站。
> 因此本节的人气投票、1–4 人组队、赛道之星、奖金、赛程时间**全部不适用**。
> 保留原文仅为留痕——**别再拿它当依据**。作废清单见 `docs/04` §10。
> 仍然成立的只有一件事：AI 评审对「可量化 + 逐条可核对」的材料更友好（见 `docs/04` §2）。

> 来源：`团聚无锡` 公众号 2026-10-15《AI切磋大会｜WaytoAGI黑客松无锡站开启报名》。
> **这是无锡站口径，不是郑州站。** 郑州站是 10/24–10/25 两天，无锡站是 10/25 单日 7 小时，赛程不能直接套；但赛道设置（同样是那 6 个）与评审机制大概率同源。

| 项 | 原文口径 | 对我们的含义 |
|---|---|---|
| 组队 | 「可以单枪上阵，也可以 **1–4 人组队**」 | 我们 3 人合规，无需凑第 4 人 |
| 交付 | 「**项目提交，演示 demo**」 | 交付的核心是**现场演示**，不是仓库。赛前 32 人时应优先投"能演"而不是"能跑全部用例" |
| 评审 | 「**评委集中打分、选手人气投票**」 | ★ **有人气投票** —— 一眼就懂、当场就有爽感的作品天然占便宜 |
| 奖项 | 全国：1024 超能大奖 1 个 + 2 个提名 + **每条赛道 3 个赛道之星**（6 赛道共 18 个）；分站前 3 名现金 | 每个赛道 3 个名额，命中率不低；「赛道之星」是按赛道评的 ⇒ **选一个不那么挤的赛道本身就有价值** |
| 算力 | 「WaytoAGI 社区提供算力支持」 | 外部 API 依赖的风险略降，但**具体提供什么模型/额度未知**，不能当已有条件 |
| 设备 | 自备笔记本电脑 | 演示环境是本机，不是云 ⇒ B 游戏「单文件 HTML 本地打开」的零翻车优势成立 |

**三条推论（会改排序）**：

1. **「人气投票」这一项，把「3 秒看懂」的权重抬高了。** A 用餐（输入 6 人 150 元 → 3 秒出 ¥148）和 B 游戏（点开就玩）在这项上明显优于 C 办公（要先听你解释"和普通总结器的区别"）。
2. **「演示 demo」是交付形式** ⇒ §4 里"3 分钟 demo 清楚度"那一行的权重应该往上调，而"代码完整度"往下调。
3. **「每条赛道 3 个赛道之星」** ⇒ 赛道拥挤度是真实成本。C 办公是公认最挤的，同样的完成度在 C 拿星的概率低于 A / B。

**失效边界**：以上三条推论建立在「郑州站评审机制与无锡站同源」这个假设上。若郑州站没有人气投票、或按全国统一标准只看两条验收线，则第 1 条推论作废（A/B 相对 C 的优势缩小，但 C 的外部依赖风险仍在）。

## 8. 基线、反悔路径与切换条件

**维持现状（不拍板）的代价**：24 日 08:30 开场时手上没有选题，赛前那 32 人时全部作废，等于把 60 人时的产能压缩到 28。现状已经空转一天多（10-21 16:10 起「选题待定」）。**维持现状不是零成本选项，是每天在烧赛前预算。**

**拍板这个动作本身的可逆性**：可逆，但成本随时间上升。

| 时点 | 反悔成本 | 回滚做法 |
|---|---|---|
| 现在 – 24 日 08:30（开场前） | 低，只损失已投入的赛前人时 | 赛前产出全部放独立分支，**不合并进 main**；反悔就丢分支，main 保持干净的协作底座 |
| 24 日 08:30 – 24 日 12:00 | 中，半天产能 | 仍可切，但只切"同一条链路能复用"的（A↔C 都吃结构化抽取） |
| 24 日 12:00 之后 | 高 | **不再切**。硬切等于交半成品，违反红线第 1 条 |

**备选触发条件**（不是"哪条更差就换"，是"出现什么读数就换"）：

| 触发读数 | 切到哪 | 为什么 |
|---|---|---|
| 开场 4h 内求解器跑不出「200 组输入 0 违反」 | A 用餐 → B 游戏 | 验收线 B 的证据拿不到，A 的核心价值消失 |
| 队友两人都不会前端、只有一人能写 JS | B 游戏 → C 办公 | 游戏纯前端，一人写不动；办公可以只做后端 + CLI 交付 |
| 现场网络 / API 额度不可用 | C 办公 → A 或 B | C 是唯一有外部依赖的 |
