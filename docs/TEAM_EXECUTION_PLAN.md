# 拾物馆：五人团队分工与交付方案

版本：1.2\
更新日期：2026年10月23日\
制作模式：方案 A，团队协助制作，已由用户确认\
适用基准：[PROJECT_PLAN.md v0.6](PROJECT_PLAN.md)、[AGENTS.md v1.0.4](../AGENTS.md)；环境与 Git 操作见 [提交手册 v1.2](提交手册.md)

本文规划职责、交付物、接口依赖和验收责任，不安排时间表。人员分配是根据本次材料提出的建议；具体姓名以团队登记为准。技术经历来自成员自述，未独立核验其项目、熟练度或可投入程度。文中的目录和任务是实施约定，不表示代码、测试或部署已经完成。

## 1. 组织方式

五人，围绕同一个产品形成五项明确交付：三维体验、制作与参观界面、业务与集成、AI 与素材处理、内容与验收。

产品以一座真实 3D 收藏柜为中心。团队接收客户素材、整理故事、获得物主确认、发布并交付链接。首版不开发客户自助注册、客户编辑后台、在线支付或独立物主审批平台。

分工的依据是每个人能负责和验证什么。AI 编码助手可以承担实现，但具体结果仍由一位人类负责人验收；不按模型名称推断交付能力，不把所有问题都交回给用户。

### 1.1 五位成员与主责

| 代号 | 对应成员 | 建议主责 | 最终交付物 |
| --- | --- | --- | --- |
| A | Codex（用户本人） | 产品取舍、3D 展柜与检视体验 | 可操作的展柜、模型接入、统一的检视行为与产品演示主线 |
| B | 另一位组员 | 团队工作台、故事界面、参观页外层 | 能录入、编辑、确认、发布的界面，以及与展柜一致的故事和音频面板 |
| C | Spring Boot / MyBatis / Vue 组员 | 核心业务、数据、权限、工程集成 | 正确保存与发布的后端、共享契约、可运行和可恢复的部署版本 |
| D | Python / Django 组员 | AI 适配、图片与音频处理、后端交叉复核 | 可调用且失败可控的 AI 模块、合规素材处理模块及相关验证 |
| E | 提交《个人技术情况说明》的组员 | 内容与样例、验收设计、独立试用、演示材料 | 三件完整样例的内容包、可复现的验收记录、服务交付与演示材料 |

A 对产品范围和最终体验作决定，C 对工程组织、接口落地和集成作决定。涉及功能取舍与工程代价的争议，由 C 说明代价，A 决定产品取舍。E 根据验证结果列出缺陷，是否达到交付标准仍按开发书和 AGENTS.md 判断。

### 1.2 为什么这样安排

- A 与 B 按产物拆分：A 处理三维状态和空间表现，B 处理业务页面与用户操作。这样避免两人同时修改同一套界面。
- C 自述更接近编码与软件架构，适合负责数据关系、事务、接口和集成；具体对 Next.js/TypeScript 的掌握仍需通过实际小模块交付确认。
- D 有 Python/Django 背景，适合承担具有清楚输入输出的外部服务与素材处理，并与 C 互相核对后端行为。不能据此假定 D 已熟悉 Node.js 或三维渲染。
- E 的材料体现了内容结构化、Agent 任务拆解、证据与验收方面的经验，并明确说明不擅长 3D 建模和独立后端框架开发。因此让 E 持续负责内容与验收，不安排其独立承担复杂建模或核心鉴权。
- 当前材料没有证明任何成员具备成熟的独立 3D 交付经验。三维部分应先验证基本交互，再扩大视觉复杂度；这个风险不能靠增加房间或增加模型掩盖。

## 2. 选定方案 A 后的产品边界

### 2.1 一次服务交付

1. 团队确认客户想纪念的对象、展馆主题、可公开范围和交付方式。
2. 客户提供旧物照片、讲述与可选原声，E 整理来源及允许用途。
3. 团队在内部工作台建馆、收录素材，AI 辅助整理展签。
4. 团队把相应版本的展签交给物主核对，取得确认后，制作者在系统内确认当前版本。
5. 团队发布该版本，验收参观链接，再交付客户。
6. 后续修改回到草稿；涉及公开内容的变化重新确认，再次发布。

客户不需要制作账号。团队工作台需要真实的服务端身份与权限校验。首版建议单团队、预置成员账号、相同制作权限；是否采用已有统一登录由 C 按部署环境落实，不扩展多租户、组织邀请和复杂角色系统。

展馆与素材的关联、公开快照和分享状态仍必须正确校验。团队内部权限简单，不代表私有数据可以放进公开目录。

### 2.2 人工确认如何落地

E 负责收集和核对物主反馈，B 负责清楚呈现待确认内容，C 负责系统中的版本和确认规则。

线下或已有沟通渠道中的物主确认，需要能对应到具体展品和文本版本。系统内的确认操作由制作人员执行；AI 不代替物主或制作人员确认。公开内容发生变化时，旧确认失效。首版不额外建设客户审批账号和审批消息系统。

### 2.3 建议样例规模

沿用开发书：六格展柜、三件完整样例；一件重点立体展品、一件简单立体展品、一件照片或票据类展品。至少一件配有获准使用、能够播放的原声。

相机、磁带和车票只是候选，最终根据真实可用素材选择。难以取得合格模型时，替换为形态更易实现的旧物，保留真实 3D 主体验。虚构演示故事、近似模型和提前制作的模型均如实标识。

MiMo Gallery 可作为空间和物品交互参考。首版仍聚焦收藏柜；不因参考网站存在多个房间，就追加大型漫游、多场景切换和小游戏。

## 3. 五个人分别怎么做

### 3.1 A：产品与 3D 展柜负责人

**负责内容**

- 确定首版观感、展品优先级和演示主线，处理新增需求的取舍。
- 实现柜体、格位、灯光、模型接入、选择与检视。
- 维护统一的查看器控制器，负责当前展品和检视状态的权威来源。
- 处理取出、旋转、缩放、放回，以及快速点击、途中返回、窗口变化。
- 负责模型的实际导入、朝向、尺度、原点和性能处理。
- 与 B 对接故事面板，与 E 核对模型近似程度和实际效果。

**第一个交付物**

一个可运行的最小柜体，放入一个立体物体，完成选择、取出、旋转和放回，并能消费共享展示数据。占位几何体只能证明交互原型可运行，不能当作最终旧物样例。

**验收标准**

检视状态采用开发书的四个状态；重复选择和动画中途退出后仍能恢复到稳定布局。故事、音频与当前选中物体一致。模型加载失败和 WebGL 不可用时，保留真实照片与故事入口。

**协作边界**

A 不同时承担全部后端、部署、测试和素材收集。需要共享契约或依赖变更时向 C 提出具体需求；不自行绕过契约读取内部数据。

### 3.2 B：工作台与故事界面负责人

**负责内容**

- 团队登录界面、展馆与展品录入、照片和音频上传入口。
- 原始讲述、AI 草稿、人工编辑与确认操作的清楚区分。
- 保存中、已保存、失败、版本冲突等状态，以及未保存输入保护。
- 发布、停止分享和更换链接的操作界面。
- 参观页外层、故事面板、照片入口、音频控制及手机图文入口。
- 使用 A 的查看器控制器显示当前展品，避免独立维护第二份选中状态。

**第一个交付物**

能依据共享契约录入和编辑一件旧物的工作台页面，含加载、保存、失败和冲突的明确呈现。接口未完成时可以使用明确标识的本地 fixture，接口就绪后接入真实保存。

**验收标准**

保存后刷新仍可恢复；AI 失败不丢输入；版本冲突不自动覆盖；未确认展品能按错误响应中的 ID 定位。参观页不泄露原始讲述和 AI 内部草稿，切换展品时停止上一段音频。支持键盘、返回入口和中文输入法组合态。

**协作边界**

B 负责错误的呈现，不在前端复制服务端发布规则；不自行更换框架、加入另一套状态库或修改数据库结构。

### 3.3 C：核心业务与工程集成负责人

**负责内容**

- 建立项目基础、依赖锁定、运行脚本、类型检查、lint、核心测试与构建入口。
- 维护公共 schema、请求响应、错误码、展示数据及数据库迁移。
- 实现团队身份、展馆和展品持久化、版本冲突与确认失效规则。
- 实现发布事务、不可变快照、分享 token、停止分享和授权素材读取。
- 接入 D 的 AI 与文件模块，负责业务编排、素材关联和数据库提交。
- 负责统一集成、部署配置、持久数据目录、备份和恢复说明。

**第一个交付物**

可运行的工程与共享契约，加上一条真实的保存和读取路径；在方案 A 的团队身份下完成校验，刷新和重启后数据仍在。先使用人工展签贯通保存、确认和发布，不等待 AI 成为前置条件。

**验收标准**

开发书规定的数据与分享不变量可在隔离的 PostgreSQL 测试库验证，上传文件不进入公开目录。生产构建可启动，实际部署环境可连接 PostgreSQL、执行迁移，重启后数据库和素材仍然有效，数据库与素材的配套备份可恢复。

**协作边界**

C 负责集成，但各模块作者负责修复自己的联调问题。C 不把 B 的 UI、A 的场景和 D 的适配器全部重写一遍。核心后端相关检查由 D 交叉复核，E 协助提供独立复现证据。

### 3.4 D：AI 与素材处理负责人

**负责内容**

- 核实可用模型服务的真实 API 调用方式，并完成服务端适配。
- 实现输入限制、超时、输出结构校验、追问数量和来源片段标识校验。
- 与 E 定义内容样例和事实核对口径，保留“约”“记不清”等不确定性。
- 实现图片和音频的格式、文件签名、解析和大小校验。
- 处理图片方向、定位及设备敏感元数据、缩略图和贴图输出。
- 为 C 提供清楚的文件处理结果和失败信息，验证文件完成但数据库提交失败等边界。
- 交叉检查 C 的权限、发布和迁移行为。

**第一个交付物**

一个能对结构化输入返回合规草稿的真实 AI 适配样例，以及一张合法照片从校验到处理输出的完整样例。聊天软件中能使用某模型，不代表已经拥有可在产品后端调用的 API；是否可用以实际调用结果为准。

**验收标准**

模型不可用或输出无效时明确失败，保留用户输入。旧 AI 结果不能覆盖新版本。图片和音频遵守开发书第 9.7 节限额，处理后的分享图片不带定位元数据；素材处理失败不会被包装成上传成功。

**协作边界**

D 的适配器与文件模块不另建一套数据库、身份或发布逻辑。C 负责权限、版本检查、数据库提交和对外路由，D 负责外部调用及字节处理；两人共同验证文件和数据库分步完成时的行为。Python 可用于开发期离线处理和验证，首版不因此默认增加 Django 常驻服务。

### 3.5 E：内容、质量与交付负责人

**负责内容**

- 把三件样例整理为统一内容包：名称、约略年代、原始讲述、来源片段、照片、可选原声、用途许可、待确认问题。
- 收集可用模型的来源与许可、真实参考照片和近似程度说明，交给 A 处理实际三维资产。
- 与物主核对故事，维护确认对应的版本和交付记录。
- 设计正常、缺失信息、不确定讲述、矛盾讲述等内容样例，检查 AI 是否保留事实边界。
- 按开发书组织验收，维护问题的复现步骤、预期、实际结果和修复后证据。
- 编写适量的内容校验脚本与端到端测试，组织真实制作与参观试用。
- 准备演示材料、样例来源清单、操作说明、实际未完成项与服务成本记录。

**第一个交付物**

一件可以直接录入的完整旧物内容包、一份与开发书验收场景对应的检查清单，以及其余样例的素材缺口。内容缺失时明确列出，不由 AI 补造。

**验收标准**

每件样例的来源与允许用途清楚；事实和 AI 整理文本分开。缺陷记录能让作者复现。完成一次实际制作与参观验证，并如实区分“觉得有意思”“愿意提供素材”“愿意分享”和“愿意付款”。少量试用反馈不等于市场已经成立。

**协作边界**

E 持续参与内容与验收，不仅在交付前写 PPT；也不承担独立复杂建模和核心安全代码签字。已有的 Agent 管理经验用来派清楚的任务，不在本项目额外搭建 Agent 调度平台、技能市场或大型评测框架。

## 4. 技术方案：保持一套运行体系

数据库已按用户要求确定为 PostgreSQL。其余建议沿用开发书的 Next.js、TypeScript、React、React Three Fiber / Three.js、Zod 和服务端持久文件目录；首版为单应用、单实例 Node 服务连接 PostgreSQL，不增加第二套业务后端。

这个建议依据当前产品和现有规划，不代表团队已经熟练掌握该栈。React 与 Fiber 需要按官方兼容关系选定版本；安装、生产构建和实际运行后才能宣布环境可用。版本锁定后，成员在同一套依赖与脚本下工作。兼容关系参考 [React Three Fiber 安装文档](https://r3f.docs.pmnd.rs/getting-started/installation)，环境复现、PostgreSQL 连接与迁移验证按 [开发书第 9.1 节](PROJECT_PLAN.md#91-建议技术方案)及提交手册执行。

C 在 G0 固定 Node.js、包管理器、PostgreSQL 与驱动版本和锁文件，并提供不含密钥的连接配置样例、独立开发库与测试库的创建方式及实际检查命令。每人使用独立工作目录；同机工作额外区分端口，Windows 与 Linux 分别安装依赖和生成构建产物。具体步骤见 [提交手册第八节](提交手册.md#八多人协作如何避免环境冲突)。

不按成员各自熟悉的技术拆成 Next.js、Spring Boot 和 Django 三套并行服务。熟悉后端框架的价值可以用于数据设计、接口、权限和排错，不必通过增加运行栈体现。

如果 C、D 在完成最小业务路径后发现现有模板无法维护，而确有经过验证、能直接部署的成熟后端工程，可以提交一次有证据的替代方案：说明能复用的内容、需要改动的契约、部署与测试代价，并由 A、C 确定是否调整。未经记录不在模块里悄悄增加服务；替代方案应明确统一的后端归属，不同时保留两套业务实现。

| `scripts/content/**`、`tests/e2e/**`、`tests/fixtures/**`、内容与验收文档 | E | 内容校验、端到端检查、可公开或脱敏的样例 |

各模块作者负责对应局部测试，不把所有测试转交 E。真实客户照片、录音、数据库和配置不提交 Git；仓库 fixture 只使用获准公开或脱敏的测试数据。

## 6. 五条必须对齐的交接

| 交接 | 交付方 → 使用方 | 必须说清楚的内容 |
| --- | --- | --- |
| 展示数据 | C → A、B | 当前公开快照、展品 ID、格位、展签、照片/音频读取方式、modelKey；不夹带原始讲述和内部草稿 |
| 检视状态 | A → B | 当前展品和检视阶段的唯一事实来源、选择/返回入口、音频切换触发条件 |
| AI 整理 | C、D → B；E 核对内容 | 来源版本、来源片段标识、草稿、最多两个追问、失败类型；采纳前重新检查版本 |
| 素材上传 | B → C → D | 输入限制、实际解析结果、处理后元数据、文件完成与数据库提交的责任、失败响应 |
| 样例与模型 | E → A、B、C | 内容包、原声与照片、模型来源和许可、近似程度、物主确认版本、缺失项 |

一个事实只维护一处权威定义。共享类型从 schema 推导；接口字段通过契约变更同步，不靠页面临时兼容多个名字。

在接口完成前，A、B 可以使用同一 schema 校验过的明确标识 fixture 开发。E 维护样例内容，C 维护字段定义；fixture 不能进入真实保存、AI 或发布的成功路径冒充服务。

## 7. 交付依赖与推进方式

本节仅描述依赖，不对应日期、工时或比赛时刻。

| 交付包 | 最终负责人 | 参与者 | 前提 | 结束条件 |
| --- | --- | --- | --- | --- |
| G0：基础与契约 | C | 各模块作者核对契约，D 验证原生依赖 | 已选择方案 A | 工程、契约和脚本可用；工具链、配置样例和独立开发数据说明齐备 |
| G1：三维交互原型 | A | B 协助面板，E 操作检查 | 展示契约草案 | 立体物体能选中、检视和返回，状态能与面板对齐 |
| G2：可用样例内容 | E | A 处理模型，B、C 核对录入结构 | 素材与允许用途 | 内容包完整，模型或照片展示方式明确，缺失信息如实列出 |
| G3：人工制作到发布 | C | B 完成界面，D 提供素材处理，E 核验 | G0、可录入内容、素材上传 | 真实保存、人工展签、确认、发布，另一浏览器看到新内容 |
| G4：AI 和完整展柜接入 | A | C 集成，D 提供 AI，B 联动界面，E 核验 | G1、G2、G3 | 真实 AI 调用与人工采纳可用，三件样例进入展柜，音频可播放 |
| G5：实际服务交付 | C | E 组织验收与材料，A 验收体验，各作者修复 | 主链路可运行 | 开发书全部适用核心验收通过，生产运行、备份恢复和交付说明齐备 |

最终负责人负责收齐成果、组织联调、跟进阻塞并报告是否达到结束条件，不代替各模块作者实现，也不免除独立复核。负责人变更在共享任务清单登记后同步本表。

G1、G2 和不涉及持久化的 AI 适配验证可以并行。G3 不以 AI 成功为前提，人工编辑也能贯通制作和发布；最终交付仍需要完成至少一次真实 AI 调用。

未通过某个交付包时，先处理阻塞它的具体问题。保存和发布未贯通时不增加新主题；模型接入未稳定时不追加复杂房间；测试暴露数据与权限问题时不以减少检查掩盖。

## 8. 验收与复核

### 8.1 责任分配

| 验证对象 | 实现主责 | 复核 / 验收 | 关键证据 |
| --- | --- | --- | --- |
| 团队身份、核心数据、迁移 | C | D 复核；E 提供独立复现 | 隔离测试数据库、失败请求、迁移与恢复结果 |
| 发布、确认与分享 | C；B 完成界面 | D 复核规则；A 验收流程；E 记录 | 确认失效、版本冲突、快照隔离、撤销后数据与素材拒绝 |
| 图片、音频与文件处理 | D；C 编排和提交 | C 复核；E 抽检 | 边界文件、格式和尺寸限制、处理后元数据、失败不误删 |
| AI 适配与草稿采纳 | D、C；B 呈现 | C 复核技术边界；E 核对事实 | 真实调用、无效输出、超时、过期结果、不确定性保留 |
| 3D 与故事联动 | A、B | E 实际操作；A/B 互查边界 | 正常检视、快速切换、返回、模型失败、WebGL 故障 |
| 生产部署与恢复 | C | E 按说明复现，相关作者配合 | 生产构建、另一浏览器和实际手机、重启与恢复后的真实数据 |

以上是分工安排，不是能力认证。复核人如果无法解释本次关键规则和验证结果，应明确说明，由 C 协调具备相应能力的成员处理；同一作者的 AI 自查不能冒充另一位人工复核。人员临时无法参与时沿用开发书第 7.1 节的单人自查规则，不另增一套审批流程。

### 8.2 完整验收与局部检查

开发书第 10 节仍是完整验收依据，本文件不缩减其检查范围。每位作者先验证自己改动的行为，E 负责组织跨模块、桌面与实际手机检查。

局部修改只运行相关验证。首次完整上线和跨核心流程改动按开发书执行完整验收。AI 服务可在边界处替换以验证错误路径，但真实 AI 演示和数据持久化不能以 mock 代替。

### 8.3 统一交付口径

每项任务交付说明包含：完成了什么、改动范围、如何复现、实际验证、未执行项、已知限制和下一位接手人。报告区分已通过、失败、未执行和受环境阻塞。

“代码已生成”“命令退出成功”“页面能打开”分别只是局部证据。功能是否完成，以该任务的行为结果和开发书要求判断。

## 9. AI 协作与变更管理

- 每项交付物有一位最终负责人。负责人可以借助已获授权的 AI 工具，但不能把“AI 说通过”当成人工验收。
- 同时工作的成员或编码助手使用独立 checkout；同机也不共用一个 Git 工作目录或可写数据目录。共享文件仍由一位明确作者修改，按依赖顺序合入。
- Git 协作采用提交手册中的任务分支、PR 复核和 Squash 合入约定；具体 Git 操作仍按现有授权执行。本分工方案本身不授予提交、推送、分支切换或子代理权限。
- 公共 schema、数据库迁移、锁文件和根配置由 C 统筹；依赖变更说明实际用途，不为了各自偏好安装重复库。
- 联调发现接口不符时，由定义的负责人修复权威实现，不在每个消费者增加不同的兼容补丁。
- 交接以可运行变更与验证证据为中心，不传递一个无法解释的整项目压缩包让别人重新拼接。
- E 的任务卡、证据记录保持简单；一个共享任务清单、一组可复现说明和必要的决策记录即可，不再开发协作平台。
